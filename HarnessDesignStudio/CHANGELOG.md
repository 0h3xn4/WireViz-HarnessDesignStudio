Everything that changed since 1.17.0 is listed below in short; the full text of each change is in the sections 1.17.1rc2 and 1.17.1rc1 of the changelog (1.17.1rc1 was never published). **Still open:** nobody has checked the signature or the attestation from outside the release workflow; the Windows packages were not tried on a real computer; nobody has looked at the new screens on a real display; and the owner has given no sign-off for this release. `1.17.1` is shorter than `1.17.1rc2`, so the stored hashes of the written files, the numbers snapshot and the migration hashes were written again: no number and no written file changes apart from the version stamp and the model hash that includes it (`docs/changes.md`, decision D-225).

The stored hashes carry the new version (D-225). No code and no written output changes, apart from the version stamp.

**Everything since 1.17.0, in short** (the full text is in the sections 1.17.1rc2 and 1.17.1rc1 of the changelog):

- **A cable can end in a loose end (the second step towards 2.0, in the core only: no screen yet).** This is the model and the rules behind "drag a cable from a port and drop it on empty ground" (decisions D-200 and D-201; the throw-away spike of it is `docs/ait/SPIKE_M4_LOOSE_END.md`). A **loose end** is the end of a cable that is not on a connector yet. It is saved like any other connector of the harness (role `loose`, with the placeholder library part `TBD-CONNECTOR`, which the tool adds when the first one is made and which the part lists do not offer), its wires and pins are the ones you drew, and it follows the same rules as every connector. What the core can do, each as one undo step: make a cable from a port with one end plugged in and the other loose; **plug** a loose end into a port (its pins are paired with the pins of the port by signal name, TX to RX included, else by pin number; where two pins would be met by number and carry different names the plug is refused and says which, so nothing is paired wrongly without a word); **unplug** a connector so that it is loose again (its pins and wires stay, its part goes back to `TBD-CONNECTOR`; a harness made from a connection keeps both ends plugged in and refuses, with the reason); and **decide** an end, by plugging it or by giving it a connector part in the Connectors tab. The **checks** say so: the design rule *Approved parts* reports *N cable end(s) have no connector chosen yet (loose end)* (a choice to make, not a part to approve; still 39 rules), and the data check refuses a loose end that says it mates, a loose end in a harness that Generate makes, and a connection that claims a harness Generate makes. The **build workbook** of a harness with a loose end gets a ninth check, *Ends not decided*, and says *Ready to build: no* until the end is decided, however complete the rest is (the independent verifier checks this again). **A harness with a loose end cannot be released** (`loose_end_unresolved`, with the ends named); `release --accept-loose-ends REASON` (at least 10 characters) releases anyway and keeps the reason in the change log and the baseline, and `--accept-unapproved-parts` does not cover it. ### Changed for you to know

- **`explain` now shows how the gauge of a wire was chosen (audit R1, owner decision 14).** `explain DIR WIRE` has a new derivation of the kind `gauge`, after the length: the gauges the search tried, from the smallest conductor up, the current limit of each after derating, which carries the current, then the voltage drop of each from there on and the first that keeps it within the limit, the settings it used and the assumptions it rests on (A-AMPACITY-AWG, A-BUNDLE-ALL, A-TEMP-FACTOR, A-DC-SOLID, A-ROUND-TRIP). It is computed on demand: `explain --all` and `derivations.json` / `derivations.csv` are byte for byte what they were, and no number, no written output and no hash changes.
- **`explain` prints the link to the model page (owner decision 15).** The text of `explain` now ends with `Model page: docs/models/<page>.md` (one line for each page that explains a kind of number it showed, in the order of the derivations), and `explain --json` gives each derivation the key `model_page` with the same path, last in the record (additive; `docs/CLI.md` lists the row `explain OBJECT`). A project without the key generates the same files byte for byte; with it, `explain DIR CONNECTOR.PIN` names the strategy in force and its rule, a change makes the harness plans out of date, and generating again re-places the pins (an earlier allocation is kept only while it was made by the same strategy). - **`diagram/marks.json` no longer keeps the marks of a deleted connection or interface.** What you dragged on a connection or an interface (label, connector boxes, bend) is dropped from the file when the thing is deleted: it is left out when the project is saved and dropped, silently, when a project is opened; a project whose marks all vanish loses the file as before. - **Two of the assumptions that were built into the program are settings now: spare contacts and an allowance on the wire in the bill of materials.** `model.bom_contact_spare_fraction` adds, for each harness and contact part, that fraction of the contacts used as spares (rounded up to a whole contact), and `model.bom_wire_allowance_fraction` adds that fraction of the metres of every wire part (assumptions `A-BOM-CONTACTS` and `A-BOM-NO-ALLOWANCE`). ### Added

From a connection, **Create harness** shows what it will add (the harness, the cable connectors, one wire for each pair), and makes it only after you agree: a harness you own, which Generate leaves alone, with length, gauge and colour empty until you enter them in *Edit wire*. - **Two roles: Systems engineer and Electrical / AIT engineer** (workshop point 23, "the tool generally is just too overcrowded", D-176, milestone M5). - **Edit a connector of a harness** (workshop point 6, D-174, milestone M3). In the **Connectors** tab, **Edit connector** sets the **Part**, **Gender**, **Keying** and **Name** of a cable connector (one undo step; the pins are not touched and a part with another number of pins is said under the fields), and **Pin of a connector** gains **Signal** and **Role** next to the function, termination, contact size and contact; **Pin ID** with **Add pin**, **Rename pin** (the wires on the pin follow) and **Delete pin** (refused while a wire uses it) change the pins of a connector of a harness you made. On a harness that **Generate** made the tab still adds no connector, but the part, gender, keying and the details of a pin can be set: the connector then belongs to you (`Connector.locked` in the harness file, written only then), Generate keeps those values and says *Edited by you*, the pins, their number, the name and the contact of each pin keep following the device, **Give back to Generate** returns it, and the warning `locked_data_lost` names an edited connector that cannot be kept. - **Library source and date (D-133)**: the parts library records where its data come from. `harness library DIR` shows and sets name, version, source and date; `harness import-parts` records the file name and checksum; the editor and `system/provenance.json` show them. - **UX/UI guidelines (owner's document, October 2026)**: the editor follows IBM Carbon (colour tokens, square corners, tabs and fields) with the bundled IBM Plex Sans and Mono fonts (D-132); a provenance file `system/provenance.json` in every set of outputs (tool version, model hash, library, settings with placeholder flags, design counts); requirement IDs on findings (card in the Problems panel, `Requirement` column in `drc_findings.csv`); error messages for damaged project files give the line and column; `harness schema FOLDER` writes JSON Schemas of the project files for editors; File > New project from an example; a toolbar filter that shows one signal class and fades the rest. Review of every guideline, with what does not apply to a model-first tool: `docs/UX_GUIDELINES_REVIEW.md`.

Design checking: optional **standard value profiles** (`harness config --apply-profile`, D-131) and eleven new rules (connector and wire voltage, temperature margin, mating cycles, one manufacturer per connector pair, wire specification, power/return separation, bundle current, shield bonding, one bundle per EMC class), each silent without its numbers and listed under *not checked*; sizing can use the bundle factor table; pin allocation can leave an unassigned contact between power and return; the wire list and labels show the EMC class when classes are used; every rule names the standard requirements it serves. Nothing changes for a project that does not use the new settings, except the line `Rules run: 33` in the design rule report.
- **Baseline standards (D-130)**: RS-422, RS-485 and CAN for communication, Micro-D 9, 15, 21, 25 and 31 pin for power and data, Ethernet (RJ45) as the alternative for high data rates, SMA for RF. New library parts (Micro-D 9, 21, 25 and 31 pin, RJ45 male and female), new interface type `ethernet`; units added in the editor get Micro-D connectors sized by what they carry (and an RJ45 for Ethernet, SMA for RF; RF used to get a D-sub). The computer and the payload carry Ethernet, and the sample, example projects, golden files, tutorial and documents follow. Older parts and interface types stay in the library.
- **Documentation for newcomers**: new `docs/INSTALL.md`, `docs/GETTING_STARTED.md` (a 45-minute tutorial whose commands are run by the test suite, with real output and drawings), `docs/CONCEPTS.md`, `docs/FAQ.md`, `docs/CLI.md` (generated from the program) and `docs/README.md` (a map of all documents); README, HOWTO, user guide, IMPORTS, KICAD, ARCHITECTURE, RELEASE, SPEC and PLAN brought up to date (Ubuntu only, helper process, templates). A test checks that every relative link and anchor in the Markdown resolves.
- **Examples and templates**: `harness new [--template blank|first-steps|small-satellite]` creates a project from an example (`--list` shows them) and `harness templates FOLDER` copies the import templates (CSV for interfaces, approved parts and segment lengths, a KiCad netlist and signal map, CI script and GitHub Actions workflow, a review checklist and **demo** engineering values for learning, which stay marked as placeholders). They ship inside the program, packages included; `python -m tools.build_examples` rebuilds the example projects and a test keeps them in sync.
- **Editor speed, with the background check**: the design rule check now runs in a helper process (D-128) instead of a thread, so it no longer stalls edits for 300 to 500 ms at stress size; with it running, rename takes 20 to 50 ms, move 22 to 65, add 55 to 80, undo about 60 and redo about 30. The overview map is drawn from boxes and lines (it painted 2,200 real items, about 300 ms), the problems list rebuilds only when the cards it shows change, and the map and list wait until you pause. Falls back to a thread if the helper cannot start.
- **Editor speed, add/undo/redo**: with the stress project and no rule check running, add unit takes about 60 ms, undo 65 to 110 ms and redo about 35 ms (were 190 to 330). The problems list and tab counts now follow on a 60 ms timer when a project has more than 1000 findings, and are built from one cheap counting pass (82,000 findings: 470 to about 100 ms); counts and open findings are computed once per change; the diagram grows in 256 px steps so one added or undone unit rarely resizes it. Known limit: while the background rule check runs on a project with tens of thousands of findings, the interface can still stall for a few hundred milliseconds (it holds Python's global lock in long native calls); running the check in a separate process would remove that.
- **Editor speed** (stress project: 200 units, 2000 links): renaming a unit takes about 35 ms (was 170 to 230), moving one 45 to 105 ms, a change while the interface table is shown 80 ms (was 370). One edit no longer repaints every unit and link: the lane backgrounds, which are as tall as the diagram, were invalidated on every edit; links whose curve did not change are left alone; the overview map follows on a 150 ms timer; the interface table keeps its rows when only values change. Regression tests count dirty regions and card builds instead of timing.
- **Platform**: Ubuntu 24.04 and newer only (D-127); CI tests on 24.04 only, the release build image is now `Dockerfile.build-24.04`. Editor speed: the problems panel builds only the cards it shows (add/undo/redo 3 to 6 times faster with many findings).
