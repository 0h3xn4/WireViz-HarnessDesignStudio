# Changelog

Versions follow semantic versioning. Every project file records the tool version that saved it.

## Unreleased

Work towards 1.7.0, the answer to the test users of 1.6.0 (plan: `docs/ait/TEST_USER_FEEDBACK_PLAN.md`, decision D-169). They did not like the harness plan PDFs and asked for a clear, actionable spreadsheet to build production harnesses from; they also said the tool felt overwhelming (planned for 1.8.0, D-171).

### Added

- **A build workbook for every harness** (D-169). `outputs/harnesses/W001/W001_build.xlsx`, a document to build from: **Start here** (ready to build yes or no, what is open: wires without length, gauge, colour or part are marked TO FIX, pins in use without a termination and parts that are not approved are marked NOTE; who authored, checked and approved the design; a sign-off block), **Cut list** (one row per wire in cut order, thick before thin, then colour, then length; the colour as a coloured cell with its name and code beside it; a value the model does not have is shown as *to fill in*), **Connectors** (one block per connector, pin by pin: signal, function, wire, colour, gauge, where it goes, termination, and tick columns for terminated, inserted and checked), **Parts** (with the approval state), **Labels**, **Tests** (the continuity and insulation tests with empty columns for the measured value, the result, the initials and the date) and **About**. Header rows stay on screen, the tables have filters, every sheet prints on A4 landscape with the version and model stamp in the footer; there are no formulas; the same design gives the same bytes. The independent output check reads the workbook cell by cell (`out_build`).

### Changed

- **The PDF drawings are optional** (D-169). `harness-design-studio export` no longer writes `drawing_A3.pdf`, `drawing_A4.pdf` and `drawing_A3_s<n>.svg` of the harnesses; add `--drawings` to write them. The system diagrams and every other file are written as before. A release writes the outputs again with the same set the last export had. In the editor the Export window has a check box **Include the PDF drawings**; it is checked only when the previous export in the folder had them, and the quick Export button keeps whatever the folder had. A set with the drawings of every harness or of none is valid. The existing per-harness workbook `W001.xlsx` and all CSV files are unchanged.

## 1.5.0 (2026-10-21; not a statement of compliance)

Version 1.5.0 answers a second request of the AIT engineers, to **create a project completely from scratch**: a harness can now be made by hand, with its connectors, pins and wires, and no interface behind it (decision D-166). It also makes the Linux package say what is missing in plain words instead of failing silently, and proves in CI that no package needs a Python on the machine (D-167).

What did not change: the file format (schema version 1; no new field, so a project saved by 1.4.0 opens as it is and a project that uses nothing new keeps byte-identical files), the 35 design rules, the command line, and every generated file of an existing project apart from the tool version it records (checked file by file, `tools/output_hashes.py`, `tests/test_output_hashes.py`). Not done, as in earlier releases: signing the packages (so Windows SmartScreen and macOS Gatekeeper still ask once), a screen-reader pass and the clean-machine installation test (waived by the owner, `compliance/DEVIATIONS.md`). Still open: what soldering needs beyond the termination column in the lists is for the AIT engineers to say; a command line equivalent of *New harness* is not built.

### Changed

- **Installers: nothing to install first, and a clear message when the machine lacks something.** The Linux, Windows and macOS packages already carry their own Python and Qt (checked: the Windows package holds `python312.dll`, the Linux one `libpython3.12`; the Linux self-test passes with no Python reachable). The CI smoke tests of the packages now run them in an environment without any Python (no `PYTHON*` variables, no virtual environment, no folder of the runner's on the PATH that holds a Python; the system folders stay, because the launcher of the macOS app needs `dirname` from `/usr/bin`), and the self-test has a step that fails when a package imports from outside its own folder. On Linux the editor now checks, before it starts, the three libraries it cannot carry (`libgl1`, `libegl1`, `libxcb1`) and whether there is a desktop session; if not, it says what is missing and the `sudo apt install` line, in the terminal and in a small window (zenity, kdialog or xmessage, when there is one) instead of a Python traceback or silence. `harness-design-studio-gui --check-system` runs only that check and `install.sh` runs it after installing and warns. See D-167.

### Added

- **A harness from nothing (answer to the AIT engineers: create a project completely from scratch).** A harness no longer has to come from Generate. **New harness…** (Drawings area, Edit menu, Ctrl+Shift+H) makes an empty draft harness; the new **Connectors** tab adds its cable connectors (a part of the library, or the other half of a unit's connector with its pins, gender and keying taken from it; pin names of your own if you like), sets the function, termination and contact size of a pin, and deletes a connector that has no wires; the wires are drawn in *Edit wire* as before. From there it is a harness like any other: checked, drawn, listed, reviewed and released. Generate leaves it, its connectors and its wires as they are; a harness that Generate made takes no connector by hand. No file format change (every field existed) and no change to any generated file. See `docs/user-manual/build-a-harness-by-hand.md` and D-166.

### Documentation

- **Documents brought up to 1.4.0.** The user manual (edit a wire, define a device and reuse it, import data with InvenTree files, export, Git, naming, wire colours, generate), the FAQ, glossary, concepts, cheat sheet, learning path, troubleshooting and tips, the user guide, both READMEs, the architecture, design and UX pages, the developer pages (tests of the 1.4.0 features, a picture script), the compliance records and the AIT plan now describe what 1.4.0 does; statements that were no longer true (the app has no button to lock a wire, a harness is never drawn by hand, there is no editor for interface types, the root changelog's latest version) were corrected, quoted model hashes and version stamps renewed, and two pictures added (`docs/img/edit-wire-tab.png`, `docs/img/devices-tab.png`, made by `python -m tools.tab_screenshots`). No code or output changes.

## 1.4.0 (2026-10-20; not a statement of compliance)

Version 1.4.0 answers the feedback of the AIT engineers (plan: `docs/ait/AIT_FEEDBACK_PLAN.md`, decisions D-160 to D-165): every wire can be edited and drawn by hand, wires can share a pin and be twisted or shielded together, pins have a function, connectors and harnesses have labels, the last commit is shown, and devices can be reused across projects.

What did not change for existing work: every new field is optional and is not written to a project file while it has its default value, so a project that does not use a new feature keeps byte-identical files and outputs (the file format stays at schema version 1). All 567 output files of the four example projects have the same SHA-256 as with release 1.2.0 apart from the tool version they record (`tools/output_hashes.py`, `tests/test_output_hashes.py`). There are 35 design rules (one new, *Several wires on one pin*). A project that uses a new field cannot be read completely by 1.3.0 (an older tool says which fields it does not know). Not done, as in earlier releases: signing the packages, a screen-reader pass and the clean-machine installation test (waived by the owner, `compliance/DEVIATIONS.md`). What soldering needs beyond the termination column in the lists is for the AIT engineers to say.

### Added

- **Edit a wire (1.4.0, M1).** The *Edit wire* tab beside *Why* in the Drawings area sets the gauge, type, colour and length of one or several selected wires, a label (printed on the wire labels instead of the signal name) and a note. Gauge, type, colour and length lock the wire, so Generate keeps them; label and note are always kept; *Reset to generated* gives the wires back to generation. One undo step; a released harness is refused with the reason. The wire list gets the columns *Label* and *Note* only when a wire has one, so every existing project keeps byte-identical files and outputs. See `docs/user-manual/edit-a-wire.md` and D-161.
- **Wires that you draw, several wires on one pin, twisting (1.4.0, M2).** In the same tab, *New wire* adds a wire between a connector and pin of the harness at each end; Generate keeps it, you can move its ends or delete it. Two wires may share a pin: the new design rule *Several wires on one pin* (`pin-shared`, 35 rules now) names each such pin, and the independent check says *pin_shared* (a warning) instead of *pin_reused* when a wire you drew is one of them. *Group* twists or shields selected wires together as a twisted pair, shielded pair, quad, coax or overall shield; Generate keeps the group; *Ungroup* takes a group you made apart. See D-162.
- **A function on every pin, labels on connectors and the harness, crimp or solder in the lists (1.4.0, M3).** A pin has a free-text *function* (Devices tab column *Function*, pasted blocks and the pinout import: a *Function* column beside a *Signal* column; the cable end copies it). A box connector has a *Label* on its card, a harness and each of its cable connectors have one in the *Labels* section of the *Edit wire* tab. `labels.csv` prints them (a cable end without a label prints the one of the box connector it plugs into; a harness with a label gets a row). The pinout tables get the columns *Function* and *Termination* only when a pin has one, so existing projects keep byte-identical lists. See D-163.
- **Who made the last change (1.4.0, M4).** The Revisions area shows a line with the last commit of the Git repository around the project folder: author, date, first line of the message, short id and branch. It is read from the repository files without starting `git` and without a network (nothing new for `docs/SECURITY.md`); only the author's name is kept. It is the last commit of the whole repository, and changes since then are not shown. No project file and no output changes. See D-164.
- **Devices for reuse, and parts lists from InvenTree (1.4.0, M5).** The Devices tab has *Save to library…* and *Add from library…*: a device with its connectors, pinouts (signal, function, contact size, termination), parts and interface types goes into a device library file (JSON), and devices from a file are added to another project as one undo step. Nothing in the project is replaced: a taken ID gets the next free one (`GYRO1-2`), parts and interface types you already have are kept. The same on the command line: `export-devices` and `import-devices` (`--list`, `--dry-run`). The parts import now also reads `.tsv` and `.json` files and the column names of an InvenTree export (the IPN is the part ID; a category path such as `Connectors/D-Sub` is read as `connector`); no connection to a server is made. Approval status is still never guessed. See D-165.

## 1.2.0 (2026-10-19; not a statement of compliance)

Version 1.2.0 is 1.1.0 plus **packages for Windows and macOS** and the changes that make the tool and its whole test suite run there. The tool is supported on Ubuntu 24.04 and newer, Windows 10 and 11 (64-bit) and macOS 13 and newer (Apple Silicon and Intel), decision D-149. The suite of about 2,800 tests passes on all three systems in CI.

What did not change: the design model, the file format (a project saved by 1.1.0 or 1.0.0 opens as it is), the 34 design rules and their results, the command line, and the generated outputs (every generated file is the same as in 1.1.0 except for the tool version and the model hash it records; the model hash includes the tool version). The tool still ships no derating or EMC values and no approved parts list (D-11, D-12): each project supplies them. The packages are not signed. This release has not been signed off by the owner (`docs/RELEASE.md` step 14, `compliance/SIGNOFF.md`).

### Added

- **Windows and macOS packages (D-149).** The release workflow now builds, for Windows 10 and 11 (64-bit), a per-user setup program made with Inno Setup (no administrator rights, a Start menu entry, `harness-design-studio` and `harness-design-studio-gui` on the user's `PATH`, an uninstaller) and a portable `.zip`, and, for macOS 13 and newer, `Harness Design Studio.app` in a `.dmg` for Apple Silicon (`arm64`) and one for Intel (`x86_64`), next to the Ubuntu `.deb` and `.tar.gz`; one `SHA256SUMS` covers all of them. Built by `tools/build_windows.py` and `tools/build_macos.py`; tested on the finished files (install, run, uninstall; mount, copy, run; the first-steps commands give byte-identical files to a source install) by `tools/smoke_package.py` in `.github/workflows/harness-packages.yml` (branches `pkg/**` and manual runs; publishes nothing) and in `release.yml`. The packages are not signed; the workflows have signing and notarization steps that run only when the repository secrets exist (`docs/RELEASE.md`, `docs/SECURITY.md`). Nothing is downloaded when a package is installed or run. Install steps: `docs/INSTALL.md`, ways D and E.
- **The test suite runs on Windows and macOS.** `.github/workflows/harness-platforms.yml` runs the whole suite on `windows-latest` and `macos-latest` for every change, with a time limit for each test so that a hang names the test.
- The packaged editor accepts `--selftest --selftest-out FILE` and writes `selftest ok` (or what failed) to the file, because the Windows editor has no console; the exit code is the result as before.

### Fixed

- **Windows: the "project is already open" protection.** The lock file that stops two copies of the tool from changing one project now works on Windows, where the earlier code (which relied on `fcntl` and on asking whether a process number is alive) did not run at all. The holder keeps the lock file open with a byte-range lock that the system drops when the process ends; a second copy is refused, and the lock of a program that was killed is taken over by exactly one new program. Linux and macOS are unchanged.
- The rule check helper process no longer stops at `os.nice` on Windows, which has no such function.
- The bundled IBM Plex fonts are TrueType files on every system (unpacked unchanged from the WOFF2 files; same licence), because Qt on Windows cannot read WOFF2 and the editor showed a fallback font there.
- Keys work the same on every system: Return or Enter on a row of a table does what a double-click does, F2 edits the cell of the pin table, and Tab reaches every button (on macOS the system setting for full keyboard access decided that before). The editor uses the Fusion widget style on every system; its look comes from the tokens anyway.
- The output verifier reported a crash instead of a finding for a workbook whose zip header names a newer zip version than Python reads (`NotImplementedError`); it is now the finding `out_unreadable`, with a regression test (found by the randomised damaged-outputs test).

### Changed

- The platform decisions D-110 and D-127 (Ubuntu only) are superseded by D-149 (Ubuntu 24.04 and newer, Windows 10 and 11, macOS 13 and newer).
- Text files are checked out with LF on every system (`.gitattributes`), so the byte-for-byte golden files match on Windows.
- `tools/build_installer.py` is split into pieces that the three platform builds share (the program builds and the allow-list check); the Linux packages are unchanged. The licence texts of the GPL-3 and LGPL-3 are kept in `packaging/licences/` for builds on systems without Debian's `common-licenses` folder; `tools/gen_scf.py` lists `.exe`, `.zip` and `.dmg` files too; `tools.release_notes complete` fails a release that lacks a package of any kind.
- The text of a GitHub release page is now a short page: what the tool is, a table with one row for each package that is attached (what it is for and how to install it), the highlights of the version, the full changelog section folded away, install steps and checksum commands for the systems whose packages are there, and the SHA-256 table. The highlights are written by hand in `docs/releases/<version>.md`; `python -m tools.release_notes check` fails without that file. The release workflow has a "notes only" run (`workflow_dispatch` with `notes_only`) that writes the text of an existing page again from the tag's changelog and the published checksums, without building or uploading anything.

## 1.1.0 (2026-10-18; not a statement of compliance)

Version 1.1.0 is 1.0.0 plus the changes listed below: the editor rebuilt against the new UX standard (a token-driven theme, the Harness, Lists, Checks, Releases and Devices tabs, the project tree and the inspector, state chips that never rely on colour alone, "Fix all", the Ctrl+K overlay, clearer link labels and pictograms); **the Devices tab, with which a device is defined down to each pin** (connectors, pins, the interface each pin carries, import of a pinout from CSV or XLSX, `import-pinout` and `export-pinout`); the rename of the folder and the commands (`harness-design-studio`, `harness-design-studio-gui`; `harness` and `harness-gui` stay as aliases); and a test run that takes about 30 minutes in CI instead of up to three hours.

What did not change: the design model, the file format (a project saved by 1.0.0 opens as it is), the 34 design rules and their results, the generated outputs (every generated file is the same as in 1.0.0 except for the tool version and the model hash it records; the model hash includes the tool version), and the command line apart from the two new commands. The tool still ships no derating or EMC values and no approved parts list (D-11, D-12): each project supplies them. This release has not been signed off by the owner (`docs/RELEASE.md` step 14, `compliance/SIGNOFF.md`).

### Added

Look and feel
- Theme: View > Theme offers System (the default, follows the operating system's light or dark scheme), Light and Dark; the choice is stored in the settings.
- Vector icons (from Lucide, ISC licence, drawn in code) for the toolbar and panels: zoom in, zoom out, fit, search, import, undo, redo and the panel close buttons have an icon and a tooltip that names the shortcut.
- State chips for pending, not checked, locked, released, out of date, pass and fail: icon, word and, for pending (dotted) and not checked (hatched), a pattern, so colour is never the only sign.
- Shared table code (`gui/tables.py`): right-aligned numbers, units in the header, sorting, filtering, Ctrl+C copies the selected cells as tab-separated text, column widths are remembered.

Diagram
- Several items can be selected (Shift-click, Ctrl-click, a rubber band, Ctrl+A); Properties shows what they have in common, and they are moved, deleted, aligned, spaced out and duplicated as one undo step (Ctrl+D, Edit menu, right-click menu).
- Find with Ctrl+F marks units and links; a right-click menu offers the same actions as the menus, with the reason for each greyed entry, and "Add unit here"; a grid and View > Snap to grid (Alt places freely).
- Marks on every unit card and link label: problems, warnings, values still to enter and "not checked yet" as a badge (icon and count); units, links and connectors that a release locks show a lock and "W001 A" and a faint released tint; the legend lists only the marks that are on the diagram. A click on a badge selects the object and asks the window to show its problems (the window does not act on that yet).
- A corner chip says whether the harnesses and the outputs are out of date, not generated, not exported or up to date.
- The "n auto" chip and the tooltip of the Auto badge say why the tool chose a connector and that it is not confirmed yet. "Why?" in the right-click menu asks the window for the same (not connected to a panel yet).
- Cards show a picture of their kind of unit, the number of connectors ("12 conn"), "+3" where connector pictures do not fit, and the "n auto" count in Guided mode too; FLIGHT or GROUND can be set per zone from the unit's menu (a viewer setting, not in the project file).

New views
- Harness tab (`gui/harness_view.py`): a header with the harness, its release state, its interfaces, the hash Generate last read and chips for design, outputs and independent check; a connector and pin table (locked pins carry a lock and name the release that locks them; pending values and auto-filled rows have their own chips), a wire table, a zoomable drawing and a Why pane for the selected wire, connector or pin, all linked by hover and selection.
- Lists tab (`gui/lists_panel.py`): the wire list, pinouts, BOM, mass and length, test tables, labels and the system BOM as sortable, filterable tables with units in the headers, Ctrl+C as tab-separated text, a banner when the design changed after Generate, and export of the visible rows as CSV or Excel ("Export table").
- Checks tab (`gui/checks_panel.py`): one row for each of the design rules with its result (pass, fail, not checked, pending), a summary strip ("34 rules: 20 passed · 2 failed · 12 not checked · 4 pending values"), the requirement IDs of each rule, the offending objects (Enter or double-click shows one), and the exact configuration value a pending rule waits for. - **Arrange diagram** (Edit/View menu): units stay in their lanes, ordered to shorten links, one undo step.
- Bottom panel capped at 45% of the window and wider toasts, so the diagram keeps room at large UI scales.
- Multi-drop interfaces (more than two units) are still not generated; they need an engineering rule (see `docs/DECISIONS.md` D-116).
