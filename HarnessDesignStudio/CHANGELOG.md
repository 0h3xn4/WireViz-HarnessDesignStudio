# Changelog

Versions follow semantic versioning. Every project file records the tool version that saved it.

## Unreleased

### Changed

- **A twisted pair is counted once in the bill of materials and the mass (release 1.11, D-188).** A wire part can say how many conductors one metre of it carries (`conductors`, 2 for a twisted pair; the parts import reads a *Conductors* column). Every wire that names the part is one conductor of it, so the BOM and the mass now count the sum of the wire lengths divided by that number: the metres of the cable. Before, a pair of two 3 m wires showed 6 m of cable (and 2× the mass). A part without the field counts as before, and the field is left out of the files while it is 1. The starter part `EX-WIRE-TWISTED-SHIELDED` has `conductors` 2; a `quad` made from that part counts two pairs. **In your own projects** set `conductors` on your pair parts (a *Conductors* column in the parts import) — the tool does not guess it. Of the files the shipped examples write, only the BOM, the mass table and `export.json` change (7 BOM files and 7 mass tables, system and harness level); every other file differs only in the model hash, which includes the parts. `tests/test_pair_part_counts.py`.
- **The Problems panel says why a waived problem is open again (release 1.11, D-187).** When a waiver no longer fits its finding (the finding changed after it was waived), the card names the earlier reason and says that the waiver no longer applies, and the *Waiver* column of the Checks panel reads "Waiver no longer fits". Before, the finding simply showed as open. `tests/test_gui_drc.py`.
- **A waiver is tied to the finding it was made for (release 1.11, D-187).** A waiver now records `finding_hash`, a short hash of the rule and the statement of the finding. While the finding says the same, nothing changes. When it says something else (a number or a name in its text changed), the waiver no longer applies: the finding is open again, and the DRC report lists it under *Waivers that no longer fit* with the old reason, so a changed problem is not silently still accepted. Waiving it again records the new hash. A waiver without the field (made before, or written by hand) applies as before, and the field is left out of the file while empty, so projects that have no waiver, and waivers made earlier, are written exactly as before. `tests/test_waiver_finding_hash.py`.
- **The documents no longer quote a model hash (D-186).** The transcripts in the tutorial, the manual, the examples page and the troubleshooting page show `<hash>`: the hash changes with the tool version, so every quoted value was stale after each release (four manual pages still showed 1.8.1 values). Nothing changes in the program or its files.

## 1.10.0 (2026-10-29; not a statement of compliance)

### Changed

- **The outer conductor of a coax is bonded at both ends (release 1.10, plan `docs/ait/RELEASE_1.10_PLAN.md`, D-182).** Generation gave every shield group the two ends of the project-wide grounding concept (`shield_end_a`, `shield_end_b`), so a coax got `floating` at one end, or `floating` at both while the concept was a placeholder. A coax group now always gets `backshell_360` at both ends, whatever the concept says; a coax that a person groups (**Group wires**) gets the same. Twisted pairs, shielded pairs, quads and overall shields still follow the concept. The rule `shield-wrong-end` no longer compares a coax with the concept (a coax is bonded at both ends by construction); `shield-unterminated` and `shield-bonding` read the new ends, so a coax that was reported only because of the concept is no longer reported, and a coax that a person set to `floating` still is. No file format change. In the shipped examples only `flatsat` has a coax (harness W005): its saved harness file and its drawing now show `backshell_360` at end B. Regenerating a project that has a coax changes that group's ends in a harness that is not released; a released harness is frozen and does not change. The model hash of `flatsat` changes with its saved harness and is quoted in every file it writes, so the stored comparison of the written files moves from the files of release 1.2.0 to a baseline (`docs/ui/OUTPUT_HASHES_BASELINE.json`, `tools/output_hashes.py`) that is renewed on purpose; the 1.2.0 file stays as a record (D-183). Of the 612 files of the four examples only the 120 of `flatsat` differ from what 1.9.0 wrote. A coax group that was generated cannot have its ends set by hand (only groups a person made can); if your practice needs another end for a coax, tell the owner: it would need a setting of its own.

- **Signal and interface on every cable pin; the requirement in the wire list and the traceability matrix (release 1.10, W2).** In `pinouts.csv` the *Signal* and *Interface* cells of a cable pin were empty unless the pin had a signal of its own, so a technician reading a connector could not see what a wire carried. A cable pin without its own value now shows the signal and the interface of the wires that end on it (different values sorted and joined with `;`); a pin of its own keeps its value, a spare pin stays empty, box pinouts are unchanged. While any interface has a requirement ID, the wire list gets a *Requirement* column after *EMC class* and `traceability.csv` one after *Routed* (an interface row shows its ID, a connection row stays empty); a project without requirement IDs keeps both tables. The independent output check mirrors both. No file format change. In the shipped examples only the pinout tables and the per-harness workbooks change (90 of the 612 files; the examples have no requirement IDs), so the stored baseline of the written files was renewed again (D-183, D-184).
- **`CLAUDE.md` is split (release 1.10, W1, D-182).** The file that gives an agent its instructions was 50 kB; it is 8.5 kB now (core rules, status, commands) and six area notes in `docs/developer/agent/` hold the rest, word for word. `tests/test_claude_md_split.py` keeps the file under 20 kB and every note linked both ways. No change for users.

### Fixed

- **The program no longer aborts when it ends while the autosave journal is still being written.** Since 1.9.0 the journal is written by a background thread; a process that ended without closing the window (a script, a test, any other way out) could end with signal 6 and the message `QThread: Destroyed while thread '' is still running` when the writer was slow. Ending the program now waits for the autosave writer and for a running design check (at most five seconds each, as closing the window does). The same exit no longer prints `Internal C++ object (MainWindow) already deleted` when a panel is hidden while the window is being deleted. Closing the window was not affected. `tests/test_exit_with_worker.py`.

## 1.9.0 (2026-10-28; not a statement of compliance)

### Added

- **A direction on a pin.** A pin can say which way its signal runs (`in`, `out` or `bidirectional`; empty means not set). It is optional and left out of the files while empty, so an existing project is written exactly as before. Where it is set it decides before any name does: the connection review reports output against output and input against input from the two directions (also for analog, discrete, LVDS, pyro and I2C clock signals, which the review otherwise leaves alone), and the pairing proposal pairs two equal `TX` names when the pins say `out` and `in`. The pinout tables and `export-pinout` get a last column *Direction* only while some pin has one; `import-pinout` reads a *Direction* column (a word that is not in, out or bidirectional stops the import and names the row; `n/a` and `passive` leave it unset). The JSON Schema of the connector files lists it. The Devices tab shows it (the edit column comes with the screens of this release).
- **The transmit and receive words are a setting.** The table of word pairs the connection review and the pairing proposal use (`TX`/`RX`, `MOSI`/`MISO`, `DOUT`/`DIN` ...) is the key `signal_counterparts` of `config/naming.json`; while it is not set the table of 1.8.1 is used, so nothing changes for an existing project. It is checked like the other configuration values (rule `config-invalid`, `config`, generation), and `harness-design-studio config DIR --counterparts "TX=RX, OUT=IN"` sets it (`default` clears it, `none` pairs equal names only). See `docs/CONFIG.md`.
- **A connection list as output (release 1.9, W2; audit findings F-02 and F-08).** A project that has connections (the links made with **Link connectors…**) now writes two more files, `system/connections.csv` and `system/connections.xlsx`, in the style of an interface control document:
  - One row for each pair of pins: connection, name, and for each end the device, connector, pin, signal and role (`power`, `return`, `ground`, `signal`, `shield`, `spare`), then the interface type the pair belongs to, the harness made from the connection and its note. The workbook has the same rows as a printable sheet, a **Summary** sheet with a line for each connection, and the stamp. Columns: `docs/OUTPUTS.md`, *Connection list*.
  - The connections are drawn with their IDs in `system/block_diagram` and listed in `system/traceability.csv`, whose first heading then reads *Interface or connection* and which gets a last column *Kind*.
  - **They need no harness.** `harness-design-studio export` no longer stops with "there are no harnesses to export" for a project that has connections, the Export window opens on it and plans the connection list in its tree (a project that was never saved first asks where to save it), the empty Outputs area offers **Export the connection list…**, and the banner *Outputs out of date* also shows for a project that only has connections. A project with neither a harness nor a connection still cannot be exported.
  - The independent output check reads the new files cell by cell (`out_connections`), checks that they exist exactly when the project has connections, that the block diagram shows every connection and that the traceability matrix lists them; the manifest and the checksums list them.
  - A project without connections writes none of this: every file keeps its bytes (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` prints *identical*). No design rule and no field was added.
- **The Systems engineer path in the screens (release 1.9, W1; audit of 1.8.0, section 3.2).** No new design rule and no file-format change: a project that does not use these features writes the same files, and `python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` prints *identical*.
  - **A first connector when you add a device.** The window *Add device* has an optional *First connector* (family, number of pins, gender, from the connector parts of the library). *No connector yet* stays the default.
  - **Add a connector inside Link connectors.** Under each device of the window; the connector is made with the connection in one undo step, and not at all if the window is cancelled.
  - **Pair by pin number** and **Paste a pairing…** (two columns from a table) in the window *Link connectors*. Both show a proposal with what was left out, and wait for *Accept the pairs*; the pairs join the table, never replace it, and nothing is saved before *Link connectors*.
  - **A card with the first open problem on the Next step page**: what is wrong, one sentence on what to do, *Show it*, *Waive…* (where the check allows a waiver) and *Approve …* for an unapproved part (after a question that says what approving means; one undo step; refused for a part marked *not approved* or locked by a release).
  - **The Devices tab shows the Role of each pin** (the role you gave, or the one taken from the signal name marked *(auto)*) and you can change it in the table.
  - **A tour of its own for the Systems engineer role** (the Next step page, the first button, Connect, the bar on the left).
- **Two people who both press Generate can merge (release 1.9, audit finding F-05).** No new design rule and no file-format change; every output keeps its bytes (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` prints *identical*).
  - **`.gitattributes` in a new project.** `harness-design-studio new` (and the New project window of the app) writes it once, like `.gitignore`; the five example projects ship it, and `ci/gitattributes` in the templates is the same text for a project made earlier. It has one effect: Git treats `generated/generation.json` as a binary file, so the merge still stops on it when both branches ran Generate (the record holds a hash of the whole design), but Git writes no conflict markers into it, the file stays valid JSON and keeps the version of the branch you are on. Every other file stays text and merges line by line. A save never rewrites or removes it.
  - **New command `harness-design-studio merge-fix DIR`.** It finds the files of the project that are in conflict (files with conflict markers, and the files that the index of Git still lists as unmerged; the tool reads the repository's own files and does not start `git`, new module `core/vcs/gitindex.py`). If `generated/generation.json` is the only one, it keeps this branch's version of it, runs `generate` and then `check`, and tells you to commit. If any other file is in conflict, it names the files and changes nothing (exit 1); `generate` or `check` blocked, and the record is put back as it was found. It writes nothing itself except that record, and a harness made by hand is never touched. `tests/test_merge_fix.py` makes real two-branch merges with `git` (with and without the `.gitattributes`, `merge-fix` against the recipe of the manual byte for byte, a refusal, the index reader against `git ls-files -u` for index versions 2, 3 and 4).
  - **The documents say what is true.** `docs/user-manual/use-git-and-ci.md`, CONCEPTS, TROUBLESHOOTING, FAQ, TIPS, the cheat sheet, FILE_FORMAT, the user guide and the command reference describe `merge-fix`, the `.gitattributes` and the files that still conflict by design: `logical/links.json` (every new connection gets the next number, so two people who each add one both create the same ID and the merge stops; sharding the file or a random part in the ID is a change of the file format and is not part of this change), `changelog.json`, `baselines/`, `layout.json` and, if kept in Git, `outputs/`.

- **Different people in a release, an optional setting (release 1.9, audit finding F-07).** A project can switch on `release_distinct_roles` in `config/naming.json` (`harness-design-studio config DIR --distinct-roles on`; `off` takes it out again and the file is as before). Off, which is the default, nothing changes: one name can still author, check and release a harness, and every file and output stays byte-identical. On: the author (who submitted the harness for review), the checker (`--checker`, required) and the person who releases must be three different people, in plain sentences (*The checker and the person who releases it must be different people, but both are 'Z'.*; letter case, width and extra spaces do not make a different person); a review, release or new revision may not be dated earlier than the latest entry of the change log or the latest baseline of any harness of the project (the rule for the same harness holds with or without the setting), nor more than one day after today; and `--by` may be left out, then the name from Git (`user.name`, read from the Git configuration files without starting Git, and never made up) is used and the command says so. The release dialogs show the rule, start with the Git name when no name was saved, ask for the checker as required and say in the hint which two names are the same. Switching the setting does not make the harness plans out of date. `docs/CONFIG.md`, `docs/user-manual/release-a-harness.md`; the editor has no switch for the setting yet.

### Changed

- **The README starts with a 10-minute tour, not with release history (audit findings F-13 and E-F4).** `HarnessDesignStudio/README.md` is 65 lines and about 700 words instead of 123 lines and 2,800 words: what the tool is, the honest limits, a numbered tour of five steps whose commands and quoted output lines a test runs (`tests/test_docs_claims.py`; the screens it names are checked against `gui/strings.py`), a short table of documents and the developer setup. The status, the release history, the feature list and the other text that stood there are in the new `docs/STATUS.md`, word for word (only relative links adjusted); the root `README.md` no longer carries the 3,300-character list of releases either and links there. `CLAUDE.md` (51 KB, now 49 KB) loses its 4,900-character status paragraph the same way: it keeps a short status with the facts an agent needs, and the paragraph is in `docs/developer/CLAUDE_HISTORY.md` word for word. `docs/developer/release.md` names `docs/STATUS.md` as the page to update at a release. No code, file format or output changed.
- **An edit, the autosave journal, the export and an undo step cost far less on a big project (release 1.9, R3; audit of 1.8.0, findings A-8, A-9, A-12 and B-08).** Nothing a person sees changes, no file format and no output byte: `python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` prints *identical*, and the 612 files of the four examples (the build workbooks included) were compared byte by byte before and after. Measured with `python -m tools.bench_incremental` on a project of 200 devices (2,000 interfaces, 150 harnesses with 20,000 wires, three 40-pin connectors on every device, 200 connections), median of three runs of five; the machine is shared and noisy, so read the ratios (numbers in `docs/ui/PERF_BASELINE.md`):
  - **One integrity check per edit, and only where the edit reached (A-8).** `History.execute` ran the whole check twice and started over whenever any connector changed. An `IntegrityTracker` now compares the project with the state it last looked at and checks again only the harnesses, connectors and other groups that changed or that read something that changed. Renaming a device 38 ms to 1.9 ms, editing a device connector 84 ms to 14 ms, editing one of 20,000 wires 43 ms to 2.5 ms. The first edit after a project is opened still pays for one full check (about 120 ms). The answer is the one the whole check gives: `tests/test_integrity_tracker.py` compares the tracker and the check with a verbatim copy of the 1.8.1 check (`tests/reference/integrity_181.py`) on 40 generated projects with 30 random edits each, after undoing edits, and after changes made without `History`.
  - **The autosave journal no longer stops the window (A-9).** The journal was built and written on the GUI thread after every pause: 0.41 s at 200 devices, 0.79 s the first time. The GUI thread now only copies the project (0.4 ms; entities are immutable) and a worker thread writes the journal; `serialize` rebuilds only the files whose objects changed (215 ms to 6.5 ms after one edit) and only those files are encoded again for the journal. An edit during a write asks for one more write when it ends. A save, a discard or opening another project stops a pending write first, so a late write cannot bring back a journal that was cleared. The journal file has the same bytes as before and restoring it gives the same project (`tests/test_journal_incremental.py`).
  - **The export reuses cell styles (B-08).** The build workbooks made 28,726 font objects for the flatsat; a cell style is now made once for each combination in a workbook (24 fonts), and the export of the flatsat without drawings takes 1.84 s instead of 3.73 s. Per-harness incremental export was not built: every written file carries the model hash of the whole project (the first line of each CSV, the footer of each sheet), so after any edit every file of every harness has other bytes anyway.
  - **An undo step holds the change, not a second copy of the harness (A-12).** `evolve` keeps the objects of the fields it does not change instead of dumping and validating them again: a step that edits one wire of a flatsat harness kept 682 kB, now 7 kB (dense project: 15 kB to 7 kB).
- **Making a harness from a connection, the pairing proposal and the review of all connections work in one pass.** A harness from a connection of 1,000 pairs took 31.7 s in 1.8.1 (each wire read every ID of the project and rebuilt the harness) and now takes about 0.1 s; the review of all connections no longer reads every connection again for each one, and the proposal finds the candidates of a pin by name instead of comparing every pair of pins. The results are the same as in 1.8.1: tests compare them with a copy of the 1.8.1 code on generated projects.
- **A warning no longer holds the Next step page** on *Fix what is marked*. Only a failed check that is an error does; with warnings left the page goes on to the next step and says *n warnings are left. They do not stop you.* (before, a new project with starter parts stayed on *Fix what is marked* for good and offered no fix).
- **The Systems engineer role stays on the Next step page or the diagram** after adding a device, generating, creating a harness from a connection or adding library devices, and its menus leave out the engineering entries (wire, harness, zone and alignment tools, the interface-first way, diagram drawing options, revisions of a harness, engineering values, the detail views). Every one is still in the command palette (Ctrl+K) and on its key; the Electrical / AIT engineer role lists them all.
- **Wording that follows what the project has.** A release blocker on the screen names the place in the program instead of a command-line command (the command line keeps its own words); Generate is the primary button only when the project has interfaces; the status bar says *Made by hand* for a project of connections or hand-made harnesses, not *Not generated*; the tour step about connecting mentions pin numbers and accepting; the message for a device with no connector says *Press Add a connector under it*.
- **Problem counts agree.** The Problems list says *Problems (14 of 24)* while a filter hides some, the Problems tab of the inspector explains in its tooltip why its number is smaller, and the chip of the independent check in the Harness tab says *Independent check passed* (and *Independent check passed; n design checks failed* while a design check fails) instead of a bare *Check passed*.

- **Python 3.14 or newer only.** The tool and the WireViz program at the repository root no longer support older Python versions (`requires-python = ">=3.14"`, `python_requires=">=3.14"`). The packages (`.deb`, `.tar.gz`, Windows setup and `.zip`) bring their own Python, so nothing changes for people who install those; installing from source needs Python 3.14 (Ubuntu 24.04 does not have it in its archive). CI, the release workflow and the build container use 3.14 only; `ruff` and `mypy` target 3.14, the code is modernised with `ruff` (`UP` rules; quoted annotations, `Optional`/`Union`/`List`, the `# -*- coding` lines), and the development tool `pip-audit` moves from 2.9.0 to 2.10.1 because 2.9.0 needs a version of `lxml` that has no 3.14 wheel. No file format, rule, output or behaviour changes; `python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` still prints *identical*.
- **Package build.** `tomli`, which the new `pip-audit` pulls into the build environment, is left out of the packages (`EXCLUDES` in `tools/build_installer.py`); the build still stops if any other undeclared package ends up inside.
- **Deeply nested files are refused on purpose.** Python 3.14 reads JSON nested hundreds of thousands of levels deep, where 3.13 and older stopped at about a thousand with a `RecursionError`. A file nested deeper than 1,000 levels (a real one has about ten) is now refused with the same message as before ("nested too deeply"), so that the answer does not depend on the Python version (`core/io/canonical.py`, `MAX_NESTING`).
- **Faster tests.** Eleven test files that rebuilt the same generated outputs or the same released project in every test now build it once per module and give each test a copy (no test, test name or assertion changed; the summed time of the non-GUI tests went from about 1,730 s to about 1,090 s on a loaded machine). New marker `slow` for the 11 tests of about 10 s or more: pull requests skip them (`-m "not perf and not slow"` in `harness-ci.yml` and `harness-platforms.yml`), the run on `master` and `tools.release_check` run them.
- **A release freezes the device pins that its wires end on (audit finding A-2).** A harness made from a connection (**Link connectors…**) or by hand has no interface to say which pins of the device connectors it uses, so the signal and the other fields of those pins were not frozen: `import-pinout --replace` changed them after the release and ended with exit 0. Now the pins that a released harness reaches with a wire are frozen the way the pins of a released interface already were (the same check, the same sentence, naming the harness), in the editor, in the data commands and in `harness-design-studio check` (a change made behind the tool is reported as `released_modified`); the other pins of the same connector stay editable. A project whose released harness has had such a pin changed since its release now gets that report from `check`. `docs/FILE_FORMAT.md`.

### Fixed

- **One limit for the wire current and the bundle current.** The rule `bundle-current` left the temperature factor out and `current-over-wire` took it in, so with a temperature factor of 0.5 the same wire was allowed 2.5 A by one and 1.25 A by the other. Both now use one function (`sizing.wire_current_limit`: ampacity times the bundle factor K times the temperature factor, the same as the wire sizing). `bundle-current` still runs while the temperature factor is not set (it counts as 1 there); both rule ids stay, so waivers and the lists keep working. No shipped example sets a table of bundle factors, so no example output changes.

## 1.8.1 (2026-10-27; not a statement of compliance)

Fixes from the audit of 1.8.0 (`docs/AUDIT_1.8.0.md`, decision D-177): no new feature, no file-format change, the design rules stay 39, and the files and outputs of a project that does not meet one of these cases are unchanged (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` prints *identical*). The one written text that changes for projects on placeholder configuration is the line *Ready to build* of the build workbook.

### Fixed

- **Connections.**
  - Connections between analog, discrete, LVDS, pyro and I2C clock pins are no longer reported as "two outputs drive against each other", and the pairing proposal now pairs them.
  - The pairing proposal recognises vendor-style names (`UART_TX` and `UART_RX`, `SPW_DOUT+` and `SPW_DIN+`, `TX_P` and `RX_P`, `MOSI` and `MISO`). It never pairs two equal transmit names or two equal receive names; a pair of that kind that you make yourself gets a warning.
  - A harness made from a connection is now checked against it: if a wire is moved, added, removed or relabelled, `validate`, `check`, `verify`, the design rules and `export` stop with a plain message.
  - A device connector with two cable plugs on it, or a pin wired by two harnesses, is reported when you check the project, and Generate reports a second plug. Making a connection or harness onto a connector that already has a plug, or onto a pin an interface uses, is refused with a reason.
  - A device joined only by a connection is no longer reported as "not connected to anything yet", and a heater connection (`HTR+`, `HTR-`) is no longer reported as "power without return".
- **Silence is not a pass.**
  - A design rule that is ready to run but has nothing to look at (no interface with a current or voltage, no EMC class) now says "not checked" with a plain note instead of "pass".
  - Wires that have no interface (harnesses drawn by hand or made from a connection) get a note saying that the current, voltage-drop and bundle checks did not run for them; the manual says so too.
  - The build workbook no longer says a bare "Ready to build: yes" when the values rest on placeholder configuration: it says "yes (values rest on placeholder configuration: ...)" and lists the placeholder files.
  - `export --drawings` no longer fails for a harness that has a connector and no wires.
- **Library.**
  - A device whose pins use a cable contact part can be added from the library (and as part of a subsystem), and a renamed device can be saved and added again.
  - One damaged or hand-edited file in the library folder no longer hides the others; it is listed with a plain sentence, with line and column for JSON errors. A key that appears twice in a library file is refused.
  - "Save to library" no longer replaces a different device of the same ID without asking: Replace, Save as a new ID or Cancel. `export-devices` refuses unless `--replace` is given. A part's approval in the library is never lowered.
  - The library list shows the file of each entry, and the counts of damaged files use words instead of "(s)".
- **Keyboard and screen.**
  - Tab now leaves every table. Before, a keyboard user with a row selected in the pair table of the Link connectors window, in the library list or in the main-window tables could not reach the buttons below. Tables where Tab moves from cell to cell (Devices pins, Units, Interfaces) keep that and leave with Ctrl+Tab.
  - Connection lines on the diagram can be reached with Tab, Space selects them and Enter opens the Link connectors window.
  - Editing in a project with many devices is faster: the diagram legend no longer rebuilds the list of all connectors for every harness connector (about 30 % faster per edit at 150 devices, over 40 % at 300).
  - The Problems panel heading reads "Waived" again, not the long toast sentence; `gui/strings.py` no longer defines a name twice (a test guards it), and 67 unused texts and 4 unused functions are gone.
  - The Inspector heading says "Device", not "Unit". Words that told people with connections to "Press Generate" now fit what the project has: the first-start tour, the empty Harness and Lists views and the project tree. A harness made from a connection or by hand is no longer labelled "Not generated".
- **Command line and files.**
  - The command line writes UTF-8 when its output is redirected or piped, so `drc project > report.md` no longer fails on names with characters such as Ω or ✓ on Windows.
  - Importing data the project already holds (pinouts, parts, KiCad netlists, build data) says "unchanged", prints "Already up to date." and exits 0, so a build can import the same file every time. A file with nothing in it is still an error.
  - `import-lengths` refuses two rows that give the same segment different lengths, and says "too large" for a huge value.
  - Open in the Outputs list and in the export window opens only files the program wrote and of a known kind; any other file is not opened, and the folder is offered instead.
