These sections were moved word for word from [`CLAUDE.md`](../../../CLAUDE.md) on 2026-10-29 (decision D-182); only this introduction is new. Read them when you work in `src/harness_design_studio/core/` (the model, the file layout, generation, the design rules, wire and connector editing, connections, the library, the KiCad import).

## Core layout (M1)
`core/model` (immutable strict models), `core/integrity.py`, `core/commands.py` (History: transactions, undo/redo), `core/io` (layout, loader, saver, migrate, fs), `core/starter.py`, `core/samples.py` (`mini3`). Format: `docs/FILE_FORMAT.md`; placeholders: `docs/PLACEHOLDERS.md`.
- Edit model objects only with `evolve()` and `History.execute`; never mutate `Project` directly outside commands/loader.
- Regenerate the golden fixture only on purpose: `python -c "from harness_design_studio.core.samples import mini3; from harness_design_studio.core.io.saver import save_project; save_project(mini3(), 'tests/fixtures/projects/mini3')"` and review the diff.
- Tests that run as root skip the read-only folder test; run the suite as a normal user in CI.

## Generation layout (M3)
`core/generate/` (`segmentation`, `wiring`, `pins`, `sizing`, `lengths`, `mass`, `naming`, `explain`, `engine`), `core/verify.py` (independent verifier), `core/model/generation.py` (record with provenance). `plan_generation(project)` is pure and returns ops + `RegenReport` + record; the GUI previews it (`GeneratePreviewDialog`), runs it in `PlanWorker` and applies it through `History`.
- Never put timestamps or history wording into provenance: a second plan must be empty and byte-identical.
- Verifier must stay independent of the generator: do not import wiring/pin logic into `core/verify.py`.
- Goldens: `tests/fixtures/projects/mini3` (written by `save_project(mini3())`, see the M1 section) and `sat15` (generated). Regenerate sat15 on purpose: `python -c "from harness_design_studio.core.samples import sat15; from harness_design_studio.core.generate.engine import generate_project; from harness_design_studio.core.io.saver import save_project; p=sat15(); generate_project(p); save_project(p,'tests/fixtures/projects/sat15')"` (delete the folder first) and review the diff.
- Text-replace patches fail silently after `ruff format`; grep to confirm they applied.

## Design rule check layout (M4)
`core/drc/` (`base` Rule/Hit, `rules` RULES registry, `report` Markdown report, `__init__` run/fix_ops/locate). Add a rule: write a check generator, register it in `RULES`, add a positive case to `POSITIVE` in `tests/test_drc.py` (a test fails if a rule has none) and make sure it stays quiet on the clean project. Rules needing numbers must stay silent while config is `null` and be listed in `_unchecked`.
- `checks.find` stays the fast synchronous logical layer; the controller merges it with background DRC results (`DrcWorker` waits for the helper process, 1.2 s after the last edit; waivers applied at display time).
- The check runs in a helper process (`gui/drc_process.py`, `core/drc/worker.py`, D-128; a thread held the GIL and stalled edits). Do not add synchronous DRC calls to edit paths. The packaged program must route `--drc-worker` first (`packaging/gui_entry.py`; `--selftest` checks it). Keep the pieces small: one pickle call holds the sender's GIL.
- Regenerate the sat15 DRC report golden on purpose: `python -m harness_design_studio.cli.main drc tests/fixtures/projects/sat15 > tests/fixtures/drc/sat15.md`.

## Incremental work (release 1.9, R3)
- `History.execute` asks `core/integrity.IntegrityTracker` (the errors of `check_integrity`, found again only where the project differs from the last look). A new integrity check that reads something new must say so in `_Reads` (what its result depends on) and, if it can only warn, is not tracked; `tests/test_integrity_tracker.py` compares the tracker with the verbatim 1.8.1 check (`tests/reference/integrity_181.py`) on random edits, and a scenario there per thing a check reads.
- `core/io/layout.serialize` remembers each file's bytes by the identity of the (immutable) objects it is made from; never mutate an entity or its lists in place. The journal (`core/recovery.journal_bytes`) is written by `gui/controller.JournalWorker` in a thread from a copy of the project; anything that clears the journal calls `ctl.stop_journal()` first. `model.base.evolve` keeps the objects of the fields it does not change. `outputs/buildsheet._cell` makes one cell style per combination and workbook.

## Connections (D-173, since 1.8.0)
`core/links.py` (no Qt): `propose_pairs(project, a_connector, b_connector)` pairs the pins of two device connectors by signal name only (equal names and the TX/RX-type counterparts, counterparts first, never by position, output to output and input to input not paired, a pin used once, pins another link pairs left out; returns a `Proposal` with `pairs`, `unpaired_a`, `unpaired_b`, `notes`); the planners `plan_add_link`, `plan_set_pairs`, `plan_rename_link`, `plan_delete_link`, `plan_set_roles` (pure, one undo step, a released harness's link refuses with the reason) and `plan_create_harness` (a harness with `generated=False`, cable connectors from `manual_harness`, one `manual` wire for each pair from `wires.plan_add_wire`, `harness_id` on the link; no length, gauge or colour); `derived_interfaces` (what a link carries, for display only, never stored), `effective_role`, `check_link`/`check_links` (the review, codes `link_dangling`, `link_pin_reused`, `link_direction_conflict`, `link_signal_mismatch`, `link_pin_unpaired`, `link_power_without_return`), `link_caption`. Model: `Link` and `PinPair` (`core/model/logical.py`), `Project.links`, `Pin.role` (power, return, ground, signal, shield, spare; empty means derived); file `logical/links.json` only while a link exists; integrity `dangling_link`, `link_pin_missing`, `link_pin_reused`, `link_same_device`; design rules `link-unpaired`, `link-direction`, `link-signal-mismatch`, `link-power-return` (39 rules; the DRC report says *Rules run: 39*; `tools/output_hashes.py` has `BASE_RULES` 39, the count when the stored baseline was written, and maps a later count back to it). Screens: `gui/link_dialog.py` (`LinkDialog`: the window Link connectors, Edit > Link connectors…, Ctrl+Shift+K, the Connect tool and C after two devices; `CreateHarnessDialog`, `harness_preview`), `gui/canvas_links.py` (the connection lines and the derived interface under the connector names), the **Connections** group of `project_tree.py`, Edit > Selected connection, Design > Check my connections (the Connections filter of `problems_panel.py`), and the Next step key `make_harness`; the interface-type Connect stays under Edit > Connect with an interface type…. **Rules:** the tool never creates a harness unprompted (only the button Create harness, after a preview, `tests/test_ui_links.py` checks it); the person's pinout is the source of truth and Generate keeps it; a field added for links is optional and left out while empty, so files stay byte-identical while no link exists (`tests/test_links_files.py`, `python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_BASELINE.json`); a link of a released harness is locked with it. ## Waivers and pair parts (release 1.11, D-187, D-188)
- A waiver is tied to the finding it was made for. `Waiver.finding_hash` (`core/model/review.py`, sparse, 12 hex characters) is set by `checks.waive_op` from `checks.finding_hash(finding)`: a hash of the rule and the finding's `title`, not of `why`. `checks.with_waiver` applies a waiver only while it has no hash or the hash still matches; otherwise the finding stays open with `waiver_changed` set, `drc.report` lists it under *Waivers that no longer fit* (`changed_waivers`), and the Problems card and the Checks panel say so (`panels.py`, `checks_panel.py`, `strings.CHECKS_WAIVER_CHANGED`). A waiver without a hash (an older file) still applies. `tests/test_waiver_finding_hash.py`, `tests/test_gui_drc.py`.
- `Part.conductors` (`core/model/library.py`, whole number 1 to 64, default 1, left out of the files while 1) says how many conductors one metre of a wire part carries (2 for a twisted pair). Each wire that names the part is one conductor of it, so the BOM (`outputs/tables.bom`) adds `length / conductors` per wire and the mass (`generate/mass.py`) `mass_per_m_g * length / conductors`; the wire list and the cut list stay one row per wire. The independent output check counts the same way from the project (`outputs/verify.py`: `_bom_rows`, `_mass`). The tool never guesses it for a project's own parts; the parts import reads a *Conductors* column (`library_import.py`). `tests/test_pair_part_counts.py`.

## Derivations (D-191, transparency work step 1)
`core/derive.py` (no Qt) says how a number was made: `Derivation` (quantity, value, unit, equation, `Input`s with unit and source, `Step`s, a `Check` of actual against limit, assumption IDs, reference, what is missing), `wire_current_limit_derivation`, `wire_voltage_drop_derivation`, `explain_wire` and `render`. It computes no result of its own: every value comes from `sizing.wire_current_limit`, `sizing.voltage_drop_v` and `lengths.wire_length`, the functions the generator and the rules call, so it cannot disagree with them; the steps are for the reader. `core/assumptions.py` lists the choices built into the program (`A-ROUND-TRIP`, `A-DC-SOLID`, `A-BUNDLE-ALL`, `A-TEMP-FACTOR`, `A-AMPACITY-AWG`) with an ID a derivation can cite; it is the seed of the registry of constants. `cli/explain.py` is the command (`explain DIR WIRE [--json]`). A new derivation is added with a test in `tests/test_derivations.py` that compares it with the number of the function it explains, and a page in `docs/models/`. S1 of the transparency work (D-191, D-193) added `core/derive_build.py` (readiness and its eight checks, the test limits, labels, colours, shield groups), `core/derive_layout.py` (pin allocation, segmentation, the choice of a connector), `core/derive_rules.py` (the limit or the comparison of every design rule: `INFO` has one entry for each rule, `explain_rule`) and `core/derive_kinds.py` (every kind of derivation with its page); the generator and the build workbook were split so that they call the same functions (`buildsheet.open_items`, `tables.wire_label_texts`, `wirecolours.signal_colour`, `generate/shields.py`, `drc/rules.wires_on_pins`, `standard_rules.emc_class_bundles`). `explain_wire` and `explain_harness` keep giving the numbers; `explain_wire_all`, `explain_harness_all` and `explain_object` give everything. A `Derivation` whose result is a text has `text`; `Derivation.known` says whether there is a result. A test (`tests/test_s1_rules.py`) walks every rule of the registry and fails for one without an explanation, and `tests/test_s1_build_layout.py` ties every kind to a page.

## Scripting interface (R11, transparency work step 7)
`api.py` (no Qt, no printing, no `sys.exit`) is the stable way to drive the tool from Python: `load_project`, `create_project`, `validate`, `run_checks`, `verify`, `generate`, `export(out=)`, `explain`, `explain_all`, `explain_finding`, `write_derivations`, `get_config`, `set_config`, `list_rules`, `list_templates`, `save_project`. It calls the functions the commands call and adds no behaviour; the result types and the code that builds them from the tool's objects are in `core/records.py` (frozen dataclasses with `to_dict()`), and the command line prints `to_dict()` of the same objects with `--json` (`cli/jsonout.py`: `Report`, `SHAPES`; the keys of every document are in `docs/CLI.md`, made from `SHAPES`). `core/validation.py` is what `validate` and `check` look at, shared by both. **Rules:** a new command that has a result in data form gets `--json` and a `SHAPES` entry (a test fails otherwise); the text of a command without `--json` stays byte for byte (the commands print through `Report.say`); a name added to `api.__all__` needs a docstring and a run of `python -m tools.gen_api_snapshot` (`tests/fixtures/api_snapshot.json`, `API_VERSION`); the examples in `docs/examples/scripting/` import only `api.__all__`. Page for developers: `docs/developer/api-stability.md`; user page: `docs/user-manual/script-the-tool.md`. Tests: `tests/test_api.py`, `test_api_stability.py`, `test_cli_json.py`, `test_scripting_examples.py`.

## Open data, the run record and mm² beside AWG (S5)
- `core/open_data.py` builds every table of `export-data` from the functions the generator, the rules and the derivations call (`sizing`, `bundle`, `lengths`, `mass`, `tables.bom_contributions`, `derive_rules.explain_rule`), never from a second copy of a formula; a test compares each number with its derivation. Pure and byte-deterministic: no time, user or path (a test scans the files); numbers are written with 12 significant digits (`num`). A new table is a `DataTable` in `all_tables`; add a test row in `tests/test_open_data.py` and, if an importer can read it, a line in `docs/IMPORTS.md`.
- `docs/examples/open-data/reproduce.py` is the independent check: it imports only `csv`, `json`, `math`, `sys` and `pathlib` (a test reads its imports) and recomputes from the files. If a model of `docs/models/` changes, the script changes with it.
- `core/run_record.py` is the only place that reads the clock or the operator. The record is written only when asked, next to the outputs (`outputs/run_record.json`, exempt in `core/outputs/verify.py`), and is in no hash and no manifest. Do not put a time or a name in any other file.
- The cross-section is for people: `units.format_gauge`, `gauge_short`, `with_area` on the screen, in `core/derive.render` and in the Assumptions text; never in a file the project hashes or the outputs write (`tests/test_numbers_snapshot.py`, `tests/test_output_hashes.py`, `tests/test_gauge_area.py`). In data it is the number `area_mm2`.
