# Status of the tool and release history

This page holds the status and the release history that stood on the front pages of the repository ([`../README.md`](../README.md) and [`../../README.md`](../../README.md)) until release 1.9. A front page should say what the tool is and how to try it in ten minutes, not list releases. The text below is the former text word for word, moved here without a change except that the relative links were adjusted to this folder (and one sentence that pointed to the Status section of the README now points to the section above); the changelog ([`../CHANGELOG.md`](../CHANGELOG.md)) has the full history, and [`releases/`](releases/) has the release page text of each version.

**Keeping it up to date.** The release procedure ([`developer/release.md`](developer/release.md)) names this page as the place that says which release is the latest published one. The two READMEs only link to it.

## Status

Version `2.0.0rc1` is **prepared** (decision D-229), not tagged or published yet: the **first release candidate of 2.0.0** and the **first release that writes format 2** (D-226, with the journal that merges of M7a, D-228), with the display fixes after 1.17.1 and the tag workflow (D-227). A project saved by 1.17.1 or older is upgraded once (the editor's question or `migrate`); afterwards a 1.x tool opens it read-only. The tag `v2.0.0rc1` is made after its pull request is merged and CI is green on the merge commit; it will be a pre-release. The text below describes `master` before that preparation.

On `master`, not in a release (decision D-226): **format 2**. The tool writes `schema_version` 2; format 2 is format 1 with the number 2 and is the format that may hold a loose cable end. A format 1 project opens upgraded in memory and is written in format 2 only by `harness-design-studio migrate` (look first with `--dry-run`) or by *Upgrade* in the editor's question, with the backup, the record and the check of 1.17.0; any other save of it into its own folder is refused. The model hash and every written file stay the same. A 1.x tool opens a format 2 project read-only. Format 2 is not frozen until 2.0.0 is tagged, and the program version stays 1.17.1. **M7a, the journal that merges, is in format 2** with its pull request (decision D-228): the change journal is `journal.jsonl`, one entry per line, each entry chained to its parent on its own branch; `.gitattributes` says `journal.jsonl merge=union`, so two branches' entries merge without a conflict and stay valid, and `merge-fix` records the merge; the step from 1 to 2 moves `journal.json` to `journal.jsonl` with every chain value kept. No written file changes. M7b (ID collisions on two branches, a merge-doctor) is open.

## What the tool does, as the README said before 1.9

Harness Design Studio is an offline desktop tool for the electrical harnesses of a spacecraft, made for systems engineers and for electrical / AIT engineers. You describe the devices and the interfaces between them; it generates the harnesses, checks them and writes the build workbook and lists. Try it on a practice project (these are the commands of Parts 1 to 3 and 6 of [`GETTING_STARTED.md`](GETTING_STARTED.md)):

The files are in `wheel-link/outputs/`. The full 45-minute tutorial is [`docs/GETTING_STARTED.md`](GETTING_STARTED.md). **Honest limits:** most of the tool was generated by an AI and the owner has not had it reviewed by anyone else (see the status below), no engineering values are supplied until your project enters them (results say *pending* or *not checked*), and the owner has not signed any release off (see the notes below).

An offline desktop tool for designing the electrical harnesses of a spacecraft.

> **Authorship and review.** Most of the code, tests and documentation were generated by Claude (Anthropic) through Claude Code, under the direction of the owner. The owner set the requirements, selected, directed, reviewed and approved the work. No person other than the owner has reviewed the tool, and it makes no claim of compliance with any standard. (The owner waived independent review, see [`compliance/DEVIATIONS.md`](../compliance/DEVIATIONS.md).) Provided as is, without warranty of any kind. Check all results before you rely on them. See sections 15 and 16 of the GPL-3.0.
>
> **Based in the WireViz repository.** This repository is a fork of [WireViz](https://github.com/wireviz/WireViz). Harness Design Studio is a separate codebase inside it. Harness Design Studio does not copy or import WireViz code. The decision is D-01 in [`docs/DECISIONS.md`](DECISIONS.md). WireViz is an export target (WireViz-style YAML, best effort). The original WireViz documentation is in the [repository README](../../README.md#original-wireviz-readme); [`../docs/INDEX.md`](../../docs/INDEX.md) is the index of all documents.

You describe the **devices** (computer, power unit, reaction wheel ...) and the **interfaces** between them. The tool generates the harnesses (connectors, pins, wires), checks them, writes a build workbook and lists for every harness (and the PDF drawings, if you ask for them), and keeps a change-controlled record of every release. A harness is the bundle of wires and connectors that joins the devices; words you do not know are in the [glossary](GLOSSARY.md).

```
 you draw                      the tool makes                  the tool writes
 devices + interfaces ──►      harnesses: connectors,   ──►    build workbook, wire lists,
                               pins, wires, with a             pinouts, BOM, test tables,
                               reason for each choice          labels, block diagram, change log
```

- **Your design is the source of truth.** Harnesses, drawings and lists are generated from it and can be regenerated at any time.
- **You can still edit what it makes.** Set the gauge, type, colour or length of a single wire, draw a wire yourself, put several wires on one pin, twist or shield wires together, give pins a function and connectors and harnesses a label; Generate keeps all of it ([`docs/user-manual/edit-a-wire.md`](user-manual/edit-a-wire.md)). A device you defined down to each pin can be saved to a device library file and added to another project.
- **You can start with less on screen.** Since 1.7.0 a **Next step** page names one thing to do at a time, with one button, and the project tree, the inspector and the Problems panel start closed. New in 1.8.0 this is the **Systems engineer** role: a first start asks *Who are you working as?* and the answer, **Systems engineer** or **Electrical / AIT engineer** (every area and panel), decides what the window shows first; **View > Role** changes it at once, and it is a view, never a permission ([`docs/user-manual/choose-your-role.md`](user-manual/choose-your-role.md)).
- **You can start from nothing.** A blank project shows an **Add a device** button for its first device (1.6.0). **New harness…** (1.5.0) makes a harness with no interface behind it; you add its connectors in the Connectors tab and draw its wires in Edit wire, and Generate leaves it as it is ([`docs/user-manual/build-a-harness-by-hand.md`](user-manual/build-a-harness-by-hand.md)).
- **You can start from your pinout.** New in 1.8.0: join two connectors pin by pin; the program proposes the pairs from the signal names on the pins, you confirm them, **Check my connections** reviews them, and **Create harness** makes a harness only when you press it ([how](user-manual/connect-two-connectors.md)).
- **You can share devices and subsystems.** New in 1.8.0: a **library folder** on a shared drive or in a Git repository holds device files and subsystem files (devices with the connections between them); **File > Library…** opens a window of its own to search it, preview an entry and add it to the project in one undo step, and **Number of these devices** says how many of a device there are. The program stays offline and writes into the folder only when you press **Save to library** ([how](user-manual/use-the-library.md)).
- **Offline.** It never uses the network (a test enforces this).
- **Reproducible.** The same design always produces byte-identical files, so Git diffs show real changes only.
- **Starts from the usual standards.** RS-422, RS-485 and CAN for communication, Micro-D (9 to 31 pin) for power and data, Ethernet as the alternative for high data rates, SMA for RF (what each one is: [glossary](GLOSSARY.md)). Other types and connectors can be added.
- **Honest about what it does not know.** Engineering values (derating, ampacity, EMC rules, approved parts; see the [glossary](GLOSSARY.md)) are never invented. Until you supply them, results say *pending* or *not checked*.

Runs on **Ubuntu 24.04 or newer**; packages for **Windows 10 and 11** are built from version 1.2.0 on ([`docs/INSTALL.md`](INSTALL.md), decision D-149); macOS is not supported (D-168). ## The steps and the practice project of the former README

## Try it in five minutes

1. **Install** (details in [`docs/INSTALL.md`](INSTALL.md)):

   ```
   sudo apt install ./harness-design-studio_<version>_amd64.deb
   harness-design-studio --version
   ```

2. **Make a practice project** from the built-in example and let the tool work on it:

   ```
   harness-design-studio new wheel-link --template first-steps
   harness-design-studio generate wheel-link
   harness-design-studio drc wheel-link
   harness-design-studio export wheel-link
   ```

   (`harness` still works as a short name for `harness-design-studio`.)

3. **Look at the result**: the build workbook of each harness (`harnesses/W001/W001_build.xlsx`, an Excel file to build the harness from) and the lists are in `wheel-link/outputs/`; the PDF drawings are written only with `harness-design-studio export wheel-link --drawings` (the build workbook and this option are new in 1.7.0). Open the project in the app (**Harness Design Studio** in the application menu, then **File > Open project…**): as a Systems engineer it opens on the *Next step* page, which names what to do next, and as an Electrical / AIT engineer it opens on the diagram (the first start asks which you are; **View > Role** changes it). The diagram is in the *Model* area, the checks in *Checks* and, in the *Drawings* area of the Electrical / AIT engineer, the *Why* explanation of every wire.

That is the whole idea. [`docs/GETTING_STARTED.md`](GETTING_STARTED.md) walks through it step by step with the real output of every command.

## Examples and templates

`harness-design-studio new --list` shows the example projects shipped with the tool. All five, with what to run and what you should see, are on the [examples page](examples/README.md). `minimal-satellite`, `flatsat` and the `design-worksheet.md` template are new in 1.0.0; the 0.1.0 packages have `blank`, `first-steps` and `small-satellite` only.

| Example | What it is |
| --- | --- |
| `blank` | An empty project with the starter parts and interface types. Start a real design here. |
| `first-steps` | Three devices, a power link and an RS-422 link. Nothing generated yet. Start here. |
| `minimal-satellite` | Seven devices, nominal only: solar array, battery, power unit, computer, radio, wheel and sun sensor. A small but realistic starting point. |
| `small-satellite` | 14 devices with redundant chains. Generate it to see a realistic system. |
| `flatsat` | A complete bench: 23 flight and ground devices, generated, with example numbers. Read [`docs/FLATSAT_EXAMPLE.md`](FLATSAT_EXAMPLE.md) for a tour. |

`harness-design-studio templates my-templates` copies templates for your own data: CSV files for interfaces, approved parts and segment lengths, example rows for the build data (strip lengths, pin contacts, accessories; new in 1.7.0), a KiCad netlist, a CI script, a GitHub Actions workflow, a **design worksheet** to plan a design on paper, a design review checklist and *demo* engineering values for learning (not engineering data). What each file is for: [`src/harness_design_studio/resources/examples/templates/README.md`](../src/harness_design_studio/resources/examples/templates/README.md).

## What is in a project, as the README said before 1.9

## What is in a project

A project is a folder of small JSON files (`project.json`, `config/`, `library/`, `logical/`, `physical/`, ...). Put it in Git. Outputs go to `outputs/` and are always safe to delete and regenerate. Format: [`docs/FILE_FORMAT.md`](FILE_FORMAT.md).
