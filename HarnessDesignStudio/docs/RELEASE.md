# Release checklist (Ubuntu 24.04 and newer, Windows 10 and 11; D-127, D-149, D-168)

This is the procedure for releasing the **tool** (a product release: a new version of Harness Design Studio). It is not how you release a harness in a project; that is described in the [user guide](guide/USER_GUIDE.md), section 9 (Review, release and revisions), and in [`HOWTO.md`](HOWTO.md).

Run `python -m tools.release_check` on the build host (Ubuntu 24.04; with Docker use `packaging/ubuntu/container/`). It covers the Linux packages; the Windows packages are built and tested by the release workflow ([Windows packages](#windows-packages-d-149-d-168) below). It performs the automated steps (1 to 11, with 7a, 8a and 11a) and writes `dist/release-docs/release-report.md`. Steps 12 to 15 are for people. Two different numbers are called "14" elsewhere in the records: the release check runs **14 automated steps** (1 to 11 plus 7a, 8a and 11a), whereas **step 14** is the owner's sign-off, a single step done by a person.

1. Versions agree in `pyproject.toml`, `harness_design_studio/__init__.py` and the top of `CHANGELOG.md` (the changelog entry says what changed and what is still open). Changes made after a release are collected under `## Unreleased`; at the next release rename that heading to the new version, and the check skips it until then. A new version also changes every file that records it, so regenerate them with their tools and read the diff (it must show only the version and the model hashes that include it): the example projects (`python -m tools.build_examples`), the fixture projects `mini3`, `sat15` and `custom_device` (commands in `CLAUDE.md`; `custom_device` with `write_fixture()` in `tests/test_device_equivalence.py`), the golden outputs (`python -m tools.gen_output_goldens`; run it with `PYTHONPATH=$PWD/src:$PWD` so it imports this checkout and not another install), the DRC report golden of `sat15`, the component table, the in-app guide, and the model hash quoted in `docs/GETTING_STARTED.md`. Write the highlights of the release page in `docs/releases/<version>.md` (a short Markdown list for readers, not the changelog; `python -m tools.release_notes check` fails without it). At release time (not with `--quick`) the check **fails** while `## Unreleased` still has text, and when the git tag `v<version>` already exists: a release needs a new version.
2. `ruff format --check`, `ruff check` and `mypy --strict` are clean.
3. The independent verifiers are clean on `mini3`, `sat15` and `sat15_full`.
4. Performance targets on the stress project: generation under 10 s, no design rule errors; export and checks complete.
5. Fuzzing and security tests pass (`HARNESS_FUZZ_EXAMPLES=5000 pytest tests/test_fuzz.py` for the long search; findings in `docs/SECURITY.md`).
6. Soak test: 3,000 random editing steps with all invariants held (`python -m tools.soak 5000 <seed>` for the long run).
7. The full test suite passes with the 90% core coverage gate (docs, goldens, GUI journeys and accessibility audit included). The release check sets `HARNESS_REQUIRE_BROWSER=1`, prints the number of skipped tests and **fails on any skip** except the permission tests that need a non-root user when it runs as root (`needs POSIX non-root`). So the release machine needs `poppler-utils` (`pdfinfo`), Chromium for playwright and PySide6 with the Qt libraries; `packaging/ubuntu/container/Dockerfile.build-24.04` installs them.
7a. The same suite passes again **without** coverage instrumentation (ECSS-Q-ST-80C 6.2.3.8); the release report keeps both results.
8. `python -m tools.gen_sbom` writes `sbom.cdx.json` and `licence-report.md` with nothing rejected (needs the wheelhouse from `python -m tools.vendor`, or network access, on the build host).
8a. `python -m tools.check_vulnerabilities`: no known vulnerabilities in the shipped dependencies (needs network access on the build host; output in `vulnerability-report.txt`). If the scan cannot run, the release check fails.
9. `python -m tools.check_reproducible`: the wheel builds identically twice.
10. `python -m tools.build_installer` then `python -m tools.build_deb`; `dist/harness-design-studio/harness-design-studio-gui --selftest` prints `selftest ok` (generates, exports and verifies a project, starts the rule check helper process and creates a project from a bundled example, all inside the package).
11. The `.deb` is extracted with `dpkg-deb -x`; its program runs the self-test and its `harness-design-studio new --list` shows the examples.
11a. `python -m tools.gen_scf` writes `scf.json` (version, commit, dependencies, SHA-256 of every source file, integrity value) and `SHA256SUMS` of the deliverables into `dist/release-docs`. Hand `SHA256SUMS` to the recipient; they check with `sha256sum -c SHA256SUMS` with the packages next to it (the names in the file have no folder; in the build tree run `cd dist && sha256sum -c release-docs/SHA256SUMS`). The tool exits with an error when `dist/` holds no package (`.deb`, `.tar.gz`, `.exe` or `.zip`) of this version (ECSS-Q-ST-80C 6.2.4.10, 6.2.4.11). The release workflow runs it once, over the packages of all platforms.
12. *(Waived by the owner on 2026-10-09, `compliance/DEVIATIONS.md` T-30.)* Run the self-test on a clean Ubuntu VM with networking disabled, installing with `sudo apt install ./harness-design-studio_<version>_amd64.deb` and, separately, with `./install.sh` from the tarball.
13. *(Waived by the owner on 2026-10-09, `compliance/DEVIATIONS.md` T-27.)* Usability sessions held and triaged (`docs/usability/README.md`); priority bugs fixed or accepted by the owner in writing.
14. *(Not waived; only the owner can give it. Given for `0.1.0rc8` on 2026-10-09 with D-10, D-11, D-12 and D-15 still open: `compliance/SIGNOFF.md`; the condition on the open decisions was waived for 0.1.0 on 2026-10-09, `compliance/DEVIATIONS.md` T-31. For 1.0.0 the owner instructed on 2026-10-12 to release and to make default decisions: D-10 and D-15 were recorded as the defaults the tool implements, and D-11 and D-12 as "each project supplies them" (D-142 to D-145, `compliance/DEVIATIONS.md` T-32); no values were supplied.)* Owner sign-off, including the open decisions D-10 and D-15, and confirmation that D-11 (derating and EMC values) and D-12 (approved parts list) have been supplied (see `docs/OPEN_DECISIONS.md`; D-20 is not needed). Remove `rcN` from the version only after sign-off.

15. *(A person's step, like 12 to 14.)* After the pull request is merged and CI is green on the merge commit: create the annotated tag `vX.Y.Z` on the merge commit (its message says which decisions are open and points to `compliance/SIGNOFF.md`) and push it. Pushing the tag starts `.github/workflows/release.yml`, which builds, verifies and publishes the release page with the `.tar.gz`, the `.deb`, the Windows setup program and `.zip` and one `SHA256SUMS` attached (it fails when the tag does not match the version or the changelog). If a tag cannot be pushed from where you work (the working session that prepared 1.0.0 got HTTP 403 on every tag push), create it on the GitHub release page instead: GitHub > Releases > Draft a new release > *Choose a tag*: type `vX.Y.Z` and select *Create new tag on publish* > target `master` > Publish. The tag push starts `release.yml`, which fills in the files and notes. A tag made this way is a plain (lightweight) tag, so its message cannot say which decisions are open; the release notes and `compliance/SIGNOFF.md` do. Versions 1.0.0 and 1.3.0 to 1.8.0 were published this way (the repository owner created the tag on the release page; 1.7.0: tag `v1.7.0` on `e5d8b1e`, workflow run 39861016560, first attempt; 1.8.0: tag `v1.8.0` on `1f7431e`, workflow run 40390285619, first attempt). The text of the page (download table, highlights, install steps, checksums) is written by `python -m tools.release_notes notes`; to change only the text of a page that exists, run the workflow by hand with the tag and *notes_only* ticked: it uses this checkout's script with the tag's changelog and the published checksums and uploads nothing. Compare the checksums on the release page with `compliance/evidence/release_X.Y.Z_SHA256SUMS`. Packages built by the workflow are built again on another machine, so their bytes can differ from the recorded ones; in that case say so in the release notes and use the `SHA256SUMS` that came with them. **After the workflow has finished, record the publication** (a documentation-only pull request, as for 1.6.0 and 1.7.0): copy the checksums of the release page to `compliance/evidence/release_X.Y.Z_SHA256SUMS` (the same bytes as the file on the release page), add the section *Publication of X.Y.Z* to `compliance/SIGNOFF.md` (who made the tag and when, the run, the checksums, what was not done), and change the status lines that name the release (`README.md` files, `docs/INSTALL.md`, `CLAUDE.md`). [`developer/release.md`](developer/release.md), section 4, has the same list.

## Windows packages (D-149, D-168)

The release workflow builds four files: the `.deb` and the `.tar.gz` (Linux, as before), and the Windows setup program and portable `.zip`. Each platform is built in a job of its own on a GitHub-hosted runner (`ubuntu-24.04`, `windows-latest`); these jobs only read the repository and hand their files on as artifacts. The last job, `release`, is the only one that publishes: it needs all of them, downloads the artifacts, checks that a file of every kind is there (`python -m tools.release_notes complete`), writes **one** `SHA256SUMS` and `scf.json` over all files (`python -m tools.gen_scf dist`), writes the notes and creates or edits the release page. A failed build or smoke test on any platform stops the release before anything is published; fix it and run the workflow again with the tag (*Run workflow*, the same tag; the page and files are replaced). An old tag (before 1.2.0) has no Windows build scripts and cannot be built again by this workflow. The releases 1.2.0 to 1.5.0 also have two macOS disk images; macOS was removed after 1.5.0 (D-168), so this workflow cannot build them again, and `notes_only` lists them under *Other files*.

**Try a change without a release.** Push to a branch named `pkg/...` or start `harness-design-studio packages (Windows)` by hand (`.github/workflows/harness-packages.yml`). It builds the same packages, runs the same smoke tests and keeps the files as workflow artifacts (`harness-design-studio-windows-x86_64`); it never publishes.

**Build one yourself.**

- Windows (64-bit, Python 3.14, Inno Setup 6 with `ISCC.exe` on the `PATH` or in its usual folder; the GitHub Windows image has it, otherwise `choco install innosetup`): `pip install -e ".[gui,dev]"`, then `python -m tools.build_windows` (add `--no-installer` for the `.zip` only). It writes `dist\harness-design-studio-<version>-windows-x86_64.zip` and `...-windows-x86_64-setup.exe`. The program folder `dist\harness-design-studio\` holds `harness-design-studio-gui.exe` (the editor, a windowed program), `cli\harness-design-studio.exe` (the command line tool, a console program) and `cli\harness.exe` (a copy under the short name), `LICENSES\` and `README-windows.txt`. The installer script is `packaging/windows/harness-design-studio.iss`.
- The script uses the program build and the allow-list check of `tools/build_installer.py`: the build fails when development tools or code that is not a declared runtime dependency ended up in a package, as on Linux.

**Smoke tests** (`python -m tools.smoke_package`, run by the workflows on the finished files, not on the build folder):

- `windows-setup FILE`: installs the setup program silently for the current user (`/VERYSILENT /SUPPRESSMSGBOXES /CURRENTUSER /DIR=<folder with spaces> /LOG=...`), checks the files, the Start menu entry, the `PATH` entries and the uninstall registration, runs the program checks below, runs the uninstaller silently and checks that the folder, the `PATH` entries, the registration and the Start menu folder are gone and the user `PATH` is as before.
- `windows-zip FILE`: extracts the `.zip` and runs the program checks.
- The **program checks**: `--version` of the command line tool (and of its `harness` alias) prints `harness <version>`; the first-steps walk-through (`new`, `validate`, `generate`, `drc`, `export`, `verify --outputs`) runs through the command line tool of the package and every file it writes is **byte-identical** to the files of the same commands run from the source install on the same machine; and the editor's `--selftest` (offscreen: edit, save, reload, generate, export, the rule check helper process, the bundled examples and fonts) reports `selftest ok`. The Windows editor has no console, so the self-test reports through its exit code and the file named by `--selftest-out`.
- **No network:** on Windows the programs are blocked from outgoing connections by firewall rules (`netsh advfirewall`) while they run, so a program that needed the network would fail. On Linux the offline guarantee rests on the test that the tool never opens a connection (`tests/test_offline.py`) and on the fact that nothing in the build adds a network module (the allow-list check).

**Signing (optional).** The packages are unsigned until the owner supplies certificates. Add these repository secrets (Settings > Secrets and variables > Actions); `release.yml` signs only when they exist, and every signing step is skipped, with the packages built unsigned, when they do not:

| Secret | Holds | Used for |
| --- | --- | --- |
| `WINDOWS_CERT_PFX_BASE64` | the code signing certificate with its private key as a `.pfx` file, base64 encoded (`base64 -w0 cert.pfx`, or `[Convert]::ToBase64String([IO.File]::ReadAllBytes("cert.pfx"))` in PowerShell) | `signtool` signs every `.exe` in the package, the setup program and (through them) the `.zip` |
| `WINDOWS_CERT_PASSWORD` | the password of the `.pfx` | the same |

Windows: the build signs the `.exe` files before they go into the `.zip` and the setup program, and then the setup program (SHA-256, with a timestamp from `http://timestamp.digicert.com`, override with `HARNESS_SIGN_TIMESTAMP_URL`); the job then checks that the signature of the setup program is *Valid*. Signing uses the network of the build machine (the timestamp server); the finished packages never do. After the first signed release, change the sentence "The packages are not signed" in `tools/release_notes.py` and in `docs/INSTALL.md`. **These signing paths could not be run when D-149 was made, because no certificate existed; try them on a branch with test secrets before the first signed release.** Which secrets exist is not visible to people without access to the settings; a workflow run shows the steps that were skipped.

**Facts to know.** The Windows setup program needs no administrator rights and writes only to the user's folders and `HKCU`. The portable `.zip` has the program files at its top (no folder around them), so Explorer's *Extract All* makes a folder named like the file. The binaries come from the PyInstaller and Python on the runner. The Windows programs are tested on GitHub's runners only; nobody has tried them on a physical Windows machine yet, and the release page says what is signed.

Check the documentation too: `docs/GETTING_STARTED.md` must still work word for word on the release candidate (the tests run its commands on the example project, but read it once as a newcomer would). Do not release while any step fails. A release candidate with open decisions is labelled `rc` and says so in its changelog.
