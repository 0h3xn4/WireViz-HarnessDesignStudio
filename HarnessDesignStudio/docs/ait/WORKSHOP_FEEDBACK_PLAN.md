## What 1.7.0 does today (from the code)

**A.** *Naming:* "Add a device" opens no dialog; it makes `DEV1`, `DEV2`, … named "Device n" and the person overwrites the name in the Devices tab (`gui/main_window.py` `add_device_flow`, `core/devices.py` `ops_add_device`). The ID cannot be chosen in the app. *Units:* the interface already mixes "unit" and "device"; the word "unit" is on about 107 lines of `gui/strings.py`, in the CLI (`--unit`), in about 1,150 places of the documents and in the file format (`Unit`, `units`, `logical/units/<subsystem>.json`), which must stay. *Problems:* unrequested signals are the status-bar button *Problems (n)* (Full only), the inspector tab *Problems (n)*, the top-bar chip, the banners (out of date, locked), the diagram corner chip and the badges on cards and links; the Simple workspace hides only the button, the count and the pending link; there is no switch "problems only when I ask". *Export:* the dialog always opens and disables *Export* with an inline notice when the project is read-only, has damaged files (`recovered`, the text "could not be loaded"), has no folder (the in-memory sample or an unsaved project) or no harness; the most plausible causes of the report are the unsaved sample or a project with damaged files; the note on the Next step page says "You will choose a folder", but the dialog has no folder chooser; the Harness-tab Export button is greyed out with the reason only in its tooltip. *RTN:* only a signal name used as data (return of `PWR`, of `SIG`); the glossary says it in one line.

**B.** Wires: gauge, type, colour, length, label, note, strip lengths are editable, in bulk for the selected wires (not "all wires of the harness", except the strip lengths). Groups: twisted pair, shielded pair, quad, coax, overall shield; a group can be made and removed, not changed (kind, ends). Cable connectors of a harness a person made: part, label and four pin fields; **not** the part, gender, keying or pin set after creation; a generated harness gets its connectors from the device. The Diagram draws devices and links; connector pictures appear on the device card (Guided) or as port rows (Expert); a link ends at the device or at the port row, with no connector at the link end and no harness path; the Harness tab draws the connectors, pins and wires.

**C.** A link (`InterfaceInstance`) needs a signal type and two endpoints; a connector-to-connector link without a type does not exist. Generate allocates pins from the type's signals. A person's pinout is used by Generate only when the pins are **fixed** (found by name) or **assigned to an interface**; a pin that only has a typed signal is reserved and kept, but the allocator puts the interface's signals on other free pins, so the person's pinout is effectively disregarded. Nothing compares two devices' pin labels or builds a link from them. There is no "check only" mode; integrity rules cover a manual harness (dangling wires, shared pins, mating mismatch, shields), several design rules do nothing for wires without an interface, and no rule compares the signal across a link. A pin has no power or return flag: "power" means the signal belongs to a power-category type; the return gap is a Generate setting checked only on pins that carry an interface.

**D.** The device library is a plain file (`harness-device-library`, buttons *Save to library…* and *Add from library…*, `export-devices`/`import-devices`); there is no managed library, no library window and no subsystem entity (`Unit.subsystem` is a free-text field). The tool is offline by design (a test forbids network code), so a shared library today means a shared file or folder. Redundancy is a mirrored second device `-R` with mirrored links; there is no quantity.

**E.** Rail of 8 (7 in Simple), top bar of 15 items, three docks in Full; the only modes are Guided/Expert (diagram detail) and Simple/Full (workspace). A role does not exist; the places that decide what is shown are `areas.py`, `MainWindow._show_area`, `_apply_workspace` and the sub-tabs of the docks, which are not filtered anywhere. There is one top-level window; every dialog is modal; the controller is shared, so a second non-modal window with the Devices view is feasible but needs the main window's flows re-wired.

## Proposed milestones (order to be confirmed by the owner)

1. **M1, quick fixes (no model change).** A new device asks for its name (and an ID that can be edited) before it exists; the word "unit" becomes "device" in the interface, the help of the command line (`--device` as an alias of `--unit`) and the documents, the file format unchanged; a switch *Problems only when I ask* (menu action, Settings, per workspace) that silences the top-bar chip, the corner chip, the banners that are not errors and the badges, while the Checks area and the Check button keep working; export: the dialog offers *Save project…* first for the sample, the notice says which file is damaged, the Harness-tab button shows its reason beside it, the Next step note is corrected; RTN explained in the glossary and in the pin tooltip as "return (ground)". Needs from the owner: how the export failure was reached.
2. **M2, the pinout is the truth, the tool checks (the connection model).** See the decisions. A link between two connectors with a pin-by-pin map and no signal type; interfaces derived from the pinouts of the two devices; labelled pins on both devices give a proposed pairing that the person confirms; Generate keeps and uses the person's pinout as it is; a *Check my connections* review (no changes) with rules for the pairing: pin counterpart, signal and direction, power and return pairs, unconnected pins; power and return recognised on a pin.
3. **M3, harness and connector editing.** Edit a harness connector (part, gender, keying, pins), change a group's kind and ends, bulk edit of gauge, colour and length for all wires of a harness, connectors shown at the link ends in the Diagram and the harness path on request.
4. **M4, the library.** A library window (non-modal) with devices and subsystems (a set of devices with the links between them), a shared library folder that anyone can point to (a folder on a shared drive or in a repository; no network code in the tool), blank projects without subsystems; redundancy by number of devices.
5. **M5, roles.** A choice of role at the first start (systems engineer, electrical/AIT engineer) that decides rail, tabs and defaults.

## M2 design: the pinout is the truth (decided 2026-10-26)

Answers of the owner: (1) the tool **proposes the pairing of pins by signal name** (never by position), the person sees and edits it before it is saved; (2) the interface-first way **stays, behind the new one**: *Connect* now links two connectors, the signal-type Connect stays in the Connect menu for projects that use interfaces and for the examples, and Generate keeps working for them; (3) **one button, Create harness**: the tool never creates a harness on its own.

**The model (all optional, left out of the files while empty).** A new object `Link` (file `logical/links.json`, key `links`; absent while the project has no link): `id`, `name` (a label), `a_connector` and `b_connector` (ids of device connectors; each belongs to a device), `pairs` (a list of `PinPair`: `a_pin`, `b_pin`), `harness_id` (set when the harness was created from the link), `note`. A pin gets an optional `role` (`power`, `return`, `ground`, `signal`, `shield`, `spare`; empty means *derived from the signal name*), so that power and return on a pin are visible and checkable. Interfaces are **derived** for display (`core/links.py` `derived_interfaces`: the pairs of a link grouped by the interface type their signals belong to, for example *CAN, 2 wires*); they are not stored, and the person never includes an interface.

**Pairing by signal name** (`propose_pairs`): two pins pair when their signal names are equal or the usual counterparts (`TX`/`RX`, `TXD`/`RXD`, `TX+`/`RX+`, `TX-`/`RX-`, `PWR`/`PWR`, `RTN`/`RTN`), and their directions fit (out to in, bidirectional and passive with anything; out to out and in to in do not pair); pins without a signal or without a counterpart are listed as *unpaired*; a pin is used once.

**Review, without changing anything** (`check_link` and rules): pin left unpaired on either side, direction conflict (out to out), signal names that differ across a pair (a warning), a power pair without a return pair on the same link, a pin used twice, a pair whose pin does not exist, a link whose connector is gone. Integrity codes `dangling_link`, `link_pin_missing`, `link_pin_reused` each get a negative test; the design rules get a positive case each.

**Create harness** (`plan_create_harness`): a harness a person owns (`generated=False`), with cable connectors that mate with the two device connectors (the existing `manual_harness` plans) and one wire per pair (`manual=True`, signal from the pin); length, gauge and colour follow in *Edit wire*; the link records `harness_id`; Generate leaves it alone. A link whose harness is released is locked with it (change control: links are diffable objects).

**Stages.** M2a: the model, the files, integrity, change control, `core/links.py` (pairing, planners, derivation, review, create harness), tests, no screen. M2b: the screens: *Link connectors* window (the two pin lists side by side with the proposed pairing), the Connect tool in both modes, the link list in the project tree, the link in the Diagram (between the connectors, labelled with the derived interface), *Create harness* on the link, *Check my connections* (the Checks area filtered to the link rules), the Next step page counts links as *Connect them* done. M2c: documents, pictures, requirements. The command line gets `links` and `add-link` later if the owner asks.

## M2 as built (2026-10-26)

Milestone M2 is built on the branch `feat/m2-links` (core 20f1f4d, screens 83ac9ec, documents and pictures in the last commit) and is part of version 1.8.0; decision D-173. Points 10 and 11 to 16 of the feedback. What a person sees:

- **Link connectors (points 11, 12, 13, 15).** *Edit > Link connectors…* (Ctrl+Shift+K), or the **Connect** tool / key **C** (click the first device, then the second), opens the window **Link connectors**: a device and a connector on each side, a **Name** (optional) and the table *Pairs of pins* (pin, signal and role of the first connector beside pin, signal and role of the second). The pairs are **proposed from the signal names on the pins, never from their position**: equal names (`PWR` with `PWR`, `RTN` with `RTN`) and the two ends of one line (`TX` with `RX`, `TXD`/`RXD`, `TX+`/`RX+`, `TX-`/`RX-`, `TXP`/`RXP`, `TXN`/`RXN`, either way round, counterparts first); where the interface types give a direction, an output is not paired with an output nor an input with an input (the notes under the table say so); a pin is used once; a pin without a signal is left unpaired; a pin another connection already pairs is not offered. The person changes, adds and removes pairs (*Change pair*, *Add pair*, *Remove pair*), gives a pin its **role** (Automatic, Power, Return, Ground, Signal, Shield, Spare) and sees what looks wrong written under the table while typing (the same review as *Check my connections*, never a message box). *Link connectors* stays off only when the connection cannot be made (the same device twice, no pair, a pin in two pairs); a warning does not forbid it. One undo step. The older way, by interface type, is under *Edit > Connect with an interface type…* (the arrow beside the Connect tool); Generate keeps working for projects that use it.
- **Connections on screen.** A **Connections** group in the project tree (*Link connectors…*, double-click to change the pairs, tooltip with the pairs, the harness and the checks); a dash-dotted line on the diagram between the two devices, labelled with the two connectors and, under it, what the pairs carry (*CAN, 2 wires*, derived by `derived_interfaces`, never stored); **Edit > Selected connection** (*Edit the pairs…*, *Rename…*, *Create harness*, *Delete connection*); the Simple workspace has the same Connect tool.
- **Check my connections (points 14, 10).** *Design > Check my connections* opens the Problems panel filtered to **Connections** and says *Every connection looks fine.* or how many things to look at; each card leads to the connection (its *Show* button). Nothing is changed. Four new design rules (39 rules): `link-unpaired`, `link-direction`, `link-signal-mismatch`, `link-power-return`; the integrity codes `dangling_link`, `link_pin_missing`, `link_pin_reused`, `link_same_device`. Power and return on a pin are visible as the **role** of the pin, derived from the signal name (`PWR` power, `RTN` return, `GND` ground) unless a person sets it; a pin with the role Spare is never asked about.
- **Create harness (the owner's answer 3).** The button (the Next step page after a connection, *Edit > Selected connection > Create harness*, the tree) opens a window that says *This adds the harness … with N cable connectors and M wires, one wire for each pair of …* and makes it only on **OK**: a harness the person owns (`generated` False, so Generate leaves it), cable connectors that mate with the two device connectors, one wire drawn by hand for each pair, no length, gauge or colour; the link records `harness_id`. The tool never creates a harness on its own. The **Next step** page counts a connection as *Connect* done and offers *Create harness* (key `make_harness`) while there is no harness and no interface.
- **Files and change control.** `logical/links.json` only while a link exists, `Pin.role` only when set; a project without connections keeps byte-identical files, the same model hash and the same outputs (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json`). A link of a released harness is locked with it, is a diffable object and is recorded in the baseline's `snapshot.links`. Format: `docs/FILE_FORMAT.md`, *Links and pin roles*.

Decisions kept: the tool never makes a harness unprompted; the person's pinout is the source of truth; Generate keeps pinouts; a released link is locked. Open points of M2:

## M3 as built (2026-10-26)

Milestone M3 is built on the branch `feat/m3-harness-editing` (from `feat/m2-links`) and is part of version 1.8.0; decision D-174. Points 6 to 9 of the feedback. The design question that the plan left open, *what to do with a generated harness*, was settled the simplest consistent way (see the second point). What a person sees:

- **Edit a connector (point 6).** In the **Connectors** tab, **Edit connector** sets the **Part** (a connector part of the library; the gender the part's description names is offered), **Gender**, **Keying** and **Name** of a cable connector; **Apply to connector** is one undo step. **Pin of a connector** gains **Signal** and **Role**; **Pin ID** with **Add pin**, **Rename pin** (the wires on the pin follow) and **Delete pin** (refused with the wire names while a wire uses it) change the pin set of a harness a person made. A part with another number of pins is said under the fields; the rule *Mating halves* (`mate-mismatch`) reads gender, keying and pin count. Planners (`core/connector_edit.py`): `plan_edit_connector`, `plan_edit_pin`, `plan_add_pins`, `plan_rename_pin`, `plan_delete_pin`, `plan_reset_connector`.
- **A generated harness is edited, and the edit is kept.** Generate rebuilds the cable connectors of a harness from the device connectors, so an edit must lock against regeneration the way a wire edit does. The model has one new sparse field, `Connector.locked` (written only when true; `docs/FILE_FORMAT.md`). An edit of the part, gender, keying or a pin's signal, role, function, termination or contact size on a generated harness sets it, and `generate/engine.py` (`_keep_edited_connector`) then keeps those values while the pin IDs, their number and the contact of each pin keep following the device (the contact is set on the device's pin since 1.7.0; the planner refuses it here and says so). The name of a generated connector follows its ID and is refused; so are adding, renaming and deleting pins (done on the device). The tab says *Edited by you* and offers **Give back to Generate**; a connector Generate cannot keep (its device connector is gone) is named in `locked_data_lost`. Simplest option: the lock is the whole connector, not each pin, so a locked connector no longer follows later changes of its pins' function or termination on the device until it is given back. Per-pin locks, renaming pins of a generated connector and a command-line way are not built.
- **Change a group (point 7).** **Change group…** in the **Edit wire** tab, shown for a group a person made: **Kind**, the **wires** (ticks) and the **shield ends A and B** in a window that says in one line what is wrong (*A quad is made of 4 wires, not 2.*); one undo step; Generate keeps the group. A group of the interface type is refused with the reason. Planners (`core/wires.py`): `plan_regroup`, `plan_set_group_ends`.
- **Edit all wires (point 8).** **Edit all wires…** (also **Edit > Edit all wires of the harness…**, Ctrl+Shift+B): gauge, type, colour and length on all wires of the harness, the selected wires or the wires of one signal, optionally only where a value is empty (`plan_bulk_wire_edit`, `bulk_targets`, `signals_of`, `wires_changed`). It is `plan_wire_edit` for many wires in one `Put`, so the wires are locked exactly like an edited wire and **Reset to generated** hands them back. Label, note and ends remain single-wire edits.
- **Connectors on the connections, the harness path (point 9).** In Expert mode, and in Guided mode with **View > Show connectors on connections** (`act-connection-ends`, setting `ui/connection_ends`, also on the Settings page, off by default), a box at each end of a connection line shows the connector name and *4 of 5 pins* (`core.links.link_ends`); the boxes are not drawn or computed while both are off. The tooltip adds **Path** (`core.links.link_path`) once a harness was made from the connection, and **Show the harness** (`act-link-show-harness`: Edit > Selected connection, the project tree, the right-click menu of the line) opens the Harness tab on it. The right-click menu of a connection line was empty in M2 (its actions were not handed to the diagram); it now lists its actions.
- **Files.** Only `Connector.locked` is new and it is written only when true; no file or output of a project that edits no connector changes (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json`, no golden changed).

Open points of M3:

- The screens were checked offscreen in the tests and in screenshots of the real window; they were not watched on a real display by a person.
- No command-line equivalent of any of these edits.
- A group's wires can be changed in *Change group…*, but the number of wires of a kind is fixed (a coax has 1).
- The *Role* of a cable pin is kept in the file; nothing is computed from it on a cable pin.
- The tests are `tests/test_connector_edit.py`, `tests/test_group_edit.py`, `tests/test_bulk_wire_edit.py`, `tests/test_link_ends.py` (no Qt) and `tests/test_ui_connector_edit.py`, `tests/test_ui_group_bulk_edit.py`, `tests/test_ui_connection_ends.py`; the requirements are REQ-HARN-02, REQ-WIRE-07, REQ-WIRE-08 and REQ-GUI-13 in `docs/REQUIREMENTS.md`. How-to: `docs/user-manual/build-a-harness-by-hand.md` (*Change a connector and its pins*), `docs/user-manual/edit-a-wire.md` (sections 9 and 10), `docs/user-manual/connect-two-connectors.md` (section 4).

## M4 as built (2026-10-26)

Milestone M4 is built on the branch `feat/m4-library` (from `feat/m3-harness-editing`) and is part of version 1.8.0; decision D-175. Points 17 to 20 of the feedback. The design points the plan left open were settled the simplest plain way; each is said here. What a person sees:

- **The library is a folder (points 17, 19).** **File > Library folder…** (also **Settings > Project**) names a folder, a setting of the person (`library/folder`). It is a shared drive or a Git checkout: the program stays offline, reads plain files and never starts Git or a network. The folder is searched two levels deep for `.json` files whose `format` is `harness-device-library` (D-165, unchanged) or the new `harness-subsystem-library`; other JSON files are ignored; hidden folders and links are not followed. Nothing is written unless the person presses **Save**; a subsystem file is never replaced. A folder that is missing or unreadable, and a damaged file, are explained in words in the window (the other files are still listed).
- **A subsystem is a set of devices with the links between them (point 17).** New file kind `harness-subsystem-library` version 1 (`docs/FILE_FORMAT.md`, *Subsystem library file*): name, description, notes, devices (the record of the device file), parts, interface types, connections (the links of `logical/links.json`, with the connector IDs of the file). `core/subsystem_library.py`: `export_subsystem`, `read_subsystem`, `write_subsystem`, `plan_subsystem_import` (all or nothing, one undo step, `Unit.subsystem` set to the name, a taken ID renamed to the next free one, connections added with `plan_add_link` on the new connectors, devices placed in one lane, nothing overwritten), `with_placements`; `core/library_folder.py`: `scan_folder`, `load_entry`, `describe_entry`, `save_devices`, `save_subsystem`. The command line has `export-subsystem` and `import-subsystem` (`--show`, `--dry-run`, `--replace`). `Unit.subsystem` stays free text; no field was added to the model.
- **A blank project holds no subsystem (point 17).** The `blank` example never had a device, so it has no subsystem; a test pins it (`tests/test_subsystem_library.py`). The only subsystem name that shows in a blank project is *general*, the default of the first device that is added by hand (unchanged; it is a name, not a subsystem of the library). The examples that bundle devices keep their subsystems, and no example or golden changed.
- **The library window (point 18).** **File > Library…** (Ctrl+Shift+O, because Ctrl+Shift+L is Arrange) and a **Library…** button on the Home page open `LibraryWindow` (`gui/library_window.py`, object name `library-window`): a window of its own, not modal, over the same controller. Left a search field (`library-search`, Ctrl+F) and a filter (`library-kind`) over the list (`library-list`: Kind, ID, Name, Contents); right the preview (`library-preview-pins` for a device, `library-preview-subsystem` for a subsystem); below **Number of these devices** (`library-number`), **Save selection to library…** (`library-save`, the devices selected in the project; the dialog `library-save-dialog` offers devices or a subsystem with a name and a description), **Add to project** (`library-add`, Enter in the list) and **Close** (Esc). It follows the theme, is reachable from the keyboard, and keeps its own size and place (`library/geometry`, `library/split`) apart from the editor's layout. The folder is read in a helper thread. The Devices tab buttons **Save to library…** and **Add from library…** are unchanged (one file, one dialog); they were not rewired to the window.
- **Redundancy is a number of devices (point 20).** `core/copies.py`: `plan_copies`, `device_count`, `copy_ids`. *Number of these devices* is in the Add device window, the Devices tab (with **Add copies**) and the library window. The number is not stored; it is counted from the devices that exist. The second device is `ID-R`, exactly what *Create redundant copy* makes (`edit.ops_redundant_copy`, which now takes a `suffix`; a test checks the two give identical files), the third and later are `ID-3`, `ID-4` ..., on the redundant chain, with the same connectors and the links mirrored where the other end has a free connector (the rest are named in the message). The number only grows and is at most 10. *Create redundant copy*, the *Chain* field and the cross-strap fix stay, and the tooltip says that it is the same as a number of 2.
- **Files.** No field was added to the model; no file or output of a project that does not use the library changes (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` stays *identical*, no golden changed). A device added with a number has the same files as one added by hand and then copied.

Open points of M4:

- Two people saving to one shared folder at the same moment can overwrite each other's device file: there is no lock and no index; the drive or Git decides. A subsystem is one file, so two subsystems never collide.
- A subsystem cannot be replaced from the window (choose another name or delete the file), and it has no version of its own.

## M5 as built (2026-10-26)

Milestone M5 is built on the branch `feat/m5-roles` (from `feat/m4-library`) and is part of version 1.8.0; decision D-176. Points 22 and 23 of the feedback. The design points that the plan left open were settled the simplest plain way; each is said here. What a person sees:

- **Two roles replace Simple and Full (point 23).** **Systems engineer** (devices, the connections between devices, subsystems, the library, the checks and the Next step page; no pinout, wire or build detail first) and **Electrical / AIT engineer** (connectors, pinouts, harnesses, wires, build sheets and tests; sees everything). The words *Simple*, *Full* and *workspace* are gone from the screen (the View menu, Settings, the Next step page, the tour, the tooltips) and from the documents and pictures. A role is a view of the program: it locks nothing, is never stored in a project (a test compares the project files after a switch) and the command line has no role.
- **What each role shows (point 22, "too overcrowded").** The **Systems engineer** has what the Simple workspace had (the side panels closed, the minimap, legend, status counts and problem notices off, the tools above the diagram reduced to *Select*, *Connect*, *Add device* and *More*, a project that opens on the Next step page) and a **rail of five areas**: Next step, Model, Checks, Revisions, Settings. *Home*, *Drawings* and *Outputs* are left out of it (the Simple workspace left out only *Home*); the harness drawings and the output files are the electrical engineer's detail. What M2 and M4 added for a systems engineer is there: the **Connections** group of the project tree, the Connect tool, *Check my connections*, **File > Library…** and, because Home is not in the rail, a **Library…** button on the Next step page next to **Show everything**. The **Electrical / AIT engineer** has what Full had: all eight areas, the panels open, the problem notices on, the diagram tools, a project that opens where it opened before; the Next step page is in the rail, not first.
- **Nothing is hidden for good.** Every area the rail leaves out is in the Go menu (Home Ctrl+7, *Go to Harness*, *Go to Lists*), on its key (Ctrl+1 to Ctrl+6), in the command palette (Ctrl+K) and in the buttons of the Next step page (**Go to Releases**, **Open the Outputs**); the rail also lists the area that is open, so the person sees where they are, and takes it off again when they leave. The sub-tabs of the side panels (project tree, device list, interfaces, inspector, why, problems) are **not** filtered by role: the plan named them as a place that decides what is shown, but the panels start closed for the Systems engineer, and filtering them would have hidden the Connections group and the device list that the role needs. The tabs of the areas follow the rail (an area a role leaves out is not listed, its tabs are not either).
- **View > Role and Settings (point 23).** **View > Role** is a submenu with two exclusive checkable actions, `act-role-systems` and `act-role-electrical`; the Settings page has a row **Role** (`settings-role`, a view of the same actions, so the menu, the page and the command palette follow each other). The switch is **at once**, with no restart, as the workspace switch was: the layout of the role that is left is saved under its own keys, the new one is loaded (panels, minimap, legend, problem notices), the open page stays and the next project that is opened starts on the first page of the role. The workspace switch had no keyboard shortcut, so none was kept.
- **The first start asks once.** A settings file with nothing stored shows a small modal window, **Who are you working as?**, before the tour: two big buttons, *Systems engineer* (*I think in devices, the connections between them, subsystems and the library.*) and *Electrical / AIT engineer* (*I work with connectors, pinouts, harnesses, wires, build sheets and tests.*), and the line *You can change this later in View > Role.* The answer is stored and its layout applied at once (a Systems engineer lands on the Next step page); closing the window without choosing means Electrical / AIT engineer. Tests and CI set a role through the hook `roles.FIRST_RUN_ROLE` (the successor of `FIRST_RUN_WORKSPACE`; `tests/conftest.py` sets `electrical`), and then no window asks; a window built with `first_run=False` (the screenshot and benchmark tools) never asks either.
- **Existing users keep working.** A settings file that already holds values and no role becomes **Electrical / AIT engineer** with no dialog. One that held the setting `ui/workspace` of 1.7.0 with the value `simple` becomes **Systems engineer**, because that was a person's choice (the old key is read once and left alone). The layout memory reuses the keys of the old workspaces (`ui/state`, `layout/<hash>/area` for the Electrical / AIT engineer; `ui/simple/state`, `layout/<hash>/simple/area` for the Systems engineer), so nobody loses a layout.
- **The tour** has a last step that points at the rail and says that what it lists depends on the role.
- **Files.** Nothing written changes: no model field, file, rule, command-line option or output (`python -m tools.output_hashes --check docs/ui/OUTPUT_HASHES_1.2.0.json` stays *identical*, no golden changed).
- **Code names.** The code says role, systems and electrical (`gui/roles.py`: `default_role`, `clean_role`, `role_key`; `gui/role_dialog.py`: `RoleDialog`; `MainWindow.set_role`, `_apply_role`, `ask_role_flow`; `areas.SYSTEMS_HIDDEN`). The one thing that keeps the old word is the layout key, `ui/simple/...`, on purpose.

Open points of M5:
