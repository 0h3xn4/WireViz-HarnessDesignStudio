This is the **first release candidate of 2.0.0**, a pre-release. It is the **first release that writes format 2**, a new version of the project file format. If you come from 1.17.1, read *Format 2: upgrade each project once* before you open a project you share with others.

### Format 2: upgrade each project once

- **What changes.** This version saves projects in format 2. Format 2 is format 1 with the number 2 in `project.json`, and the change journal in `journal.jsonl` instead of `journal.json`. Your design does not change: the model hash, the stamp in every written file, the baselines of released harnesses and every written file stay the same.
- **Nothing is upgraded without you.** A project saved by 1.17.1 or older is in format 1. This version reads it, but saves it only after you upgrade it. Commands that save (`generate`, the imports, `override`, `release` and the others) refuse a format 1 project and write nothing; `validate`, `check`, `drc` and `export` still read it.
- **How to upgrade.** In the editor, open the project and answer the question *This project is in format 1. Upgrade?* with **Upgrade** (or **Open read-only** to look only). On the command line, look first with `harness-design-studio migrate DIR --dry-run` (it writes nothing), then run `harness-design-studio migrate DIR`. The upgrade checks itself and puts every file back if anything differs.
- **The backup.** The upgrade keeps the original files in the folder `.migration-backup-v1/` inside the project, with the record `MIGRATION.json`. Git ignores this folder. Keep it until you have looked at the upgraded project.
- **Older versions.** After the upgrade, versions 1.x open the project read-only (*saved by a newer version of the tool*); they cannot save it. Everyone who edits a shared project needs this version or a later one.
- The steps, with the output to expect: [Upgrade a project to format 2](https://github.com/0h3xn4/wireviz_harness-design-studio/blob/v2.0.0rc1/HarnessDesignStudio/docs/user-manual/upgrade-a-project.md).

### The main changes

- **The change journal merges with Git.** The journal is now `journal.jsonl`, one entry per line, and a save only adds lines at the end. Each entry names the entry before it on its own branch, so the entries of two branches both stay valid after a merge. The `.gitattributes` of a project says `journal.jsonl merge=union`, so Git keeps both sides' lines and the journal does not conflict; the upgrade adds that line. `harness-design-studio merge-fix` records the merge in the journal.
- **Loose cable ends are saved in format 2.** A cable let go on empty ground (since 1.17.1) is now saved in a format that 1.x tools open read-only. So 1.17.0 can no longer set such a harness aside by mistake.
- **Text in the editor is not cut off.** The project name in the top bar shows whole, the cards of the Problems tab wrap in a narrow panel, and a message over the diagram fits the diagram.
- **The release tag can be made by a workflow** that checks the commit and its tests first.

### Known limits

- **A release candidate.** Format 2 is not frozen until 2.0.0 is tagged. Step M7b of the plan (two branches that make the same ID, and a tool that helps after such a merge) is not done.
- **The merge of the journal was tried with `git merge` in the tests only.** Whether the *Merge* button of the GitHub web site honours `merge=union` is not checked.
- **Nobody has looked at the screens on a real display**, and the Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values are placeholders until your project supplies them.
