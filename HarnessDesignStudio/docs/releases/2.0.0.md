This is **version 2.0.0**, the full release of what the release candidate 2.0.0rc1 tested, with the fixes of its end-to-end test. It is the **first full release that writes format 2**, a new version of the project file format. **Format 2 is frozen with this release:** it does not change any more, and a later change of the file format would be a new format with its own upgrade. If you come from 1.17.1, read *Format 2: upgrade each project once* before you open a project you share with others. The guide is *Upgrade a project to format 2* in the user manual (`docs/user-manual/upgrade-a-project.md`).

### Format 2: upgrade each project once

- **What changes.** This version saves projects in format 2. Format 2 is format 1 with the number 2 in `project.json`, and the change journal in `journal.jsonl` instead of `journal.json`. The upgrade changes no design data: the model hash, the findings, the baselines of released harnesses and a full export are the same before and after it.
- **Nothing is upgraded without you.** A project saved by 1.17.1 or older is in format 1. This version reads it, but saves it only after you upgrade it. Commands that save (`generate`, the imports, `override`, `release` and the others) refuse a format 1 project and write nothing; `validate`, `check`, `drc` and `export` still read it.
- **How to upgrade.** In the editor, open the project and answer the question *This project is in format 1. Upgrade?* with **Upgrade** (or **Open read-only** to look only; the banner then says why the project is read-only, and its button **Upgrade…** asks again). On the command line, look first with `harness-design-studio migrate DIR --dry-run` (it writes nothing), then run `harness-design-studio migrate DIR`. The upgrade checks itself and puts every file back if anything differs.
- **Export once after the upgrade.** The upgrade does not touch the files in `outputs/`. Export them once with this version: `verify --outputs` compares them with the version that runs, so outputs written by 1.17.1 fail it. `migrate` and the editor say so when it applies.
- **The backup.** The upgrade keeps the original files in the folder `.migration-backup-v1/` inside the project, with the record `MIGRATION.json`. Git ignores this folder. Keep it until you have looked at the upgraded project.
- **Older versions.** After the upgrade, versions 1.x open the project read-only (*saved by a newer version of the tool*); they cannot save it. The `journal` command of 1.17.1 does not see `journal.jsonl` and says the project has no journal: it is there. Everyone who edits a shared project needs this version or a later one.

### The main changes

- **The change journal merges with Git.** The journal is now `journal.jsonl`, one entry per line, and a save only adds lines at the end. Each entry names the entry before it on its own branch, so the entries of two branches both stay valid after a merge. The `.gitattributes` of a project says `journal.jsonl merge=union`, so Git keeps both sides' lines and the journal does not conflict; the upgrade adds that line. `harness-design-studio merge-fix` records the merge in the journal.
- **Loose cable ends are saved in format 2.** A cable let go on empty ground (since 1.17.1) is now saved in a format that 1.x tools open read-only. So 1.17.0 can no longer set such a harness aside by mistake.
- **Text in the editor is not cut off.** The project name in the top bar shows whole, the cards of the Problems tab wrap in a narrow panel, and a message over the diagram fits the diagram.
- **The release tag can be made by a workflow** that checks the commit and its tests first.

### Fixed since 2.0.0rc1

- **The read-only banner names the right reason.** A format 1 project opened with **Open read-only** said it was saved by a newer version or open in another window. It now says the project is in format 1 and offers **Upgrade…**.
- **`check` no longer warns `not_canonical`** on `project.json` of an untouched format 1 project.
- **`validate` and `check` say how to upgrade** a format 1 project (`harness-design-studio migrate DIR`, or **Upgrade** in the editor), instead of saying that a save would write it.
- **The upgrade guide** now says to export once after the upgrade, and what the `journal` command of 1.17.1 says of a format 2 project.

### Known limits

- **Step M7b of the plan is not done:** two branches that make the same ID (for example two new harnesses `W005`) still conflict in Git, and there is no tool yet that helps after such a merge.
- **The merge of the journal was tried with `git merge` in the tests only.** Whether the *Merge* button of the GitHub web site honours `merge=union` is not checked.
- **Nobody has looked at the screens on a real display**, and the Windows packages were built and tested on GitHub's runners only, not on a real Windows computer. The Windows packages have no Windows code-signing certificate, so SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**.
- **No compliance and no sign-off is claimed.** The configuration values are placeholders until your project supplies them.
