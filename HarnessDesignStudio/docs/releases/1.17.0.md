This release is about preparing a later upgrade of your projects. **Nothing that the tool writes changes, and no number changes:** the calculations, the 39 design rules, every table and drawing and your project files are as in 1.16.0, apart from the tool version in the stamps and the model hash that follows from it. The file format stays 1. What is new is the safety net that will be used when a newer file format comes, and a test lane that looks at the windows on real window systems.

### The main changes

- **A project in an older format is upgraded only when you agree.** When you open a project that is in an older file format, the editor now asks once: *This project is in format N. Upgrade? A copy of the original stays in .migration-backup-vN. Older tools can no longer edit it.* You can choose **Upgrade**, **Open read-only** or **Cancel**. Until 1.16.0 the editor brought such a project up to date at the first save without asking.
- **`harness-design-studio migrate DIR --dry-run` shows what an upgrade would do and writes nothing.** It lists the files that would change, the objects by kind before and after, the model hash before and after, a full export before and after, and anything that could not be carried over. It ends with exit code 0 only if nothing would be lost.
- **`migrate` keeps a backup and a record, and checks itself.** Before it writes anything it copies every file to the folder `.migration-backup-v<N>/` and writes `MIGRATION.json` there (from and to format, tool version, a SHA-256 of every file before and after, the model hash, the counts). After the write it checks that the model hash, the findings of `validate` and `check`, the baselines of released harnesses and a full export are what they were. If anything differs or the write fails, every file is put back from the backup and the command says so. A run that was killed half-way is put right by the next one.
- **The model hash no longer depends on the format number.** An upgrade to a later format will not change a hash or the 12 characters on a written file, and the baselines of released harnesses keep matching.
- **The window tests now also run on real window systems, and the quick path has a click budget.** A new check on GitHub, *harness-design-studio real platform*, runs the layout audit and the sweep over every dialog and window on Qt's real `xcb` platform (Ubuntu) and `windows` platform (the Windows runner), and the mouse tests of connecting two devices. A test also plays New project, Add device twice, Connect and Export diagram in Quick mode and fails if it needs more than 11 clicks or 5 dialogs. This is in the tests and in GitHub's checks only; the program is not changed by it.
- **The documents were brought up to date after 1.16.0:** the READMEs, the user manual, the how-tos, the reference pages and the in-app guide (F1) describe the tool as it is, and the screenshots of the window were drawn again.

### Upgrading

There is nothing to do for a project in format 1, which is the format every release writes (`schema_version` is 1 in `project.json`): it opens and saves as it is, and `migrate --dry-run` says it is up to date. Only a project from the oldest tools (format 0, with no `schema_version` in `project.json`) is asked about. For that one, run `harness-design-studio migrate DIR --dry-run` to see what would happen, then `harness-design-studio migrate DIR`, or answer **Upgrade** in the editor. The original files stay in `.migration-backup-v0/` in the project folder; the folder is not put in Git (it is in the `.gitignore` that `new` writes), so keep it as long as you want a way back. A tool older than 1.17.0 can no longer edit a project that was upgraded. The files that `export` writes are the same as before, apart from the tool version in the stamp and the model hash that follows from it.

### Known limits

- **Nobody has looked at any of this on a real display.** The question *Upgrade?* and every other window were tested with Qt's offscreen platform and, now, on the virtual display of Ubuntu and the Windows runner of GitHub; a person has not looked at them on a monitor, so please look and report what you see.
- **There is still only one file format.** The first real upgrade beyond the old format 0 to 1 has not been run; the safety net was tested with a fake format 2 that exists only in the tests. A project with a damaged file, a file that is a link, or an upgrade that would lose objects is refused. Other commands that save, for example `generate`, still bring a format-0 project up to date by saving, with the backup but without the record and the check. A kill in the last moment leaves the record at `started` (the project itself is whole).
- **The real-platform check is not a required check** of the repository, so a pull request can be merged while it is red. It finds overlapping or cut-off widgets and wrong minimum sizes; it is not a person looking at a monitor, it covers two window systems and the fonts of two machines, and no window manager runs under the virtual display.
- **No compliance and no sign-off is claimed.** The owner has not signed this release off. The packages are not signed (Windows SmartScreen shows *Windows protected your PC*: **More info**, then **Run anyway**), the configuration values are placeholders and the parts are example parts.
