- **New: ask the tool how a number was made.** `harness-design-studio explain DIR OBJECT` answers for a wire (its length, the current its gauge may carry after derating, its voltage drop and its share of the mass), for a harness (its mass, itemised), for a part of the library (why `system/bom.csv` has the quantity it has) and for `INTERFACE.CONNECTOR` (for example `IF-001.GPSU1-J01`: the contact-current limit the rule `current-over-contact` used). `--json` prints the same as data. The numbers come from the very functions the generator and the design rules call, so an explanation cannot disagree with the number it explains (a test compares them wire by wire).
- **What an explanation shows.** The equation; the inputs with units and where each comes from (a key of `config/*.json`, a field of the design, or the program); the steps; what the result is checked against (actual, limit, margin); and the assumptions built into the program that it rests on, each with an ID: `A-ROUND-TRIP`, `A-DC-SOLID`, `A-BUNDLE-ALL`, `A-TEMP-FACTOR`, `A-AMPACITY-AWG` (wire sizing), `A-SERVICE-LOOP`, `A-PATH-UNIQUE` (wire length), `A-MASS-SCOPE`, `A-MASS-CONDUCTORS` (mass), `A-BOM-CONTACTS`, `A-BOM-NO-ALLOWANCE` (bill of materials) and `A-CONTACT-SHARED` (contact current). A value that is not set is named, never made up. The pages `docs/models/` explain the models for wire sizing, wire length, mass, the bill of materials and the contact current, with worked examples.
- **New: Show the calculation in the Why tab.** Select a wire or a harness and press **Show the calculation**: the same text as `explain` appears below the recorded reasons. It is closed until you ask for it, so the tab stays short.
- **New: every derivation as files.** `harness-design-studio explain DIR --all --out FOLDER` writes `derivations.json` and `derivations.csv` (one row each; filter *Verdict* `fail` or *Missing* in a spreadsheet). There is no time, user name or path in them, so the same design gives the same bytes. Nothing in the project is changed.
- **Fixed: `validate` checks the configuration.** With `bundle_derating` set to 1.5 `validate` printed `0 error(s)` and exited 0, while `generate`, `drc` and `config` rejected the value. It now prints the same `config_invalid` error and exits 1. A project whose values are valid gets the same output as before.
- **Fixed: Table 6-41 is cited only for the table of the ECSS profile.** The note on a sized wire named the standard's table for any table of bundle factors. For a table of your own it now names `config/derating.json, bundle_factor_by_count`. The note is stored in the generation record, so a project with a bundle-factor table of its own gets a new model hash.
- **Unchanged.** No calculated number, no design rule (still 39) and no written file changes, apart from the tool version in the stamp and the model hash that follows from it (and the note above). `docs/ui/OUTPUT_HASHES_BASELINE.json` is not written again (`1.10.0`, `1.11.x` and `1.12.0` have the same length), and `python -m tools.output_hashes --check` and `python -m tools.numbers_snapshot --check` print *identical*.
- **Not in this release / for you to know.** This is the first part of the transparency work. Still to come: a registry of the constants as settings, selectable models, overrides with a reason and a history, import records, a scripting interface, plug-ins and the capture of as-built data for the Electrical / AIT role. The explanations exist for wire sizing, wire length, mass, the bill of materials and the contact current; not yet for readiness, test limits, pin allocation and the other design rules, and the findings do not yet show actual, limit and margin themselves (the explanation does). Nobody looked at the program on a real display. The packages are not signed, the configuration values are placeholders and the parts are example parts. Nobody has signed this release off as the owner; this page is not a statement of compliance with any standard.
