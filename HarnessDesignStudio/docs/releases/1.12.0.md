This is the transparency release. Until now the tool gave you numbers; from this release it also shows how it made each of them, which settings and assumptions they rest on, and what you changed by hand and why. It is made for the systems engineer who has to answer "where does this come from?", for the electrical engineer who has to check a gauge, a drop or a margin by hand, and for the AIT engineer who builds the harness and records what was built. Nothing is hidden behind the default screen: the new views open when you ask for them.

The file format keeps its schema version (1) and there is no migration. Everything new is in optional files that a project may or may not have (`config/model.json`, `imports/records.json`, `journal.json`, `asbuilt/records.json`, the folder `extensions/`). The four packaged examples and eleven checked scenarios write the same files as before (apart from the tool version in the stamp and the model hash that follows from it), the 39 design rules are unchanged, and a calculation gives the same number as in 1.11.1 unless you choose another setting.

- **AIT engineer:** `docs/user-manual/record-what-was-built.md`, `docs/user-manual/import-data.md` and `docs/user-manual/follow-the-workflow.md`.

### 1. Explain everything

- `harness-design-studio explain DIR OBJECT` prints how a number was made: the equation, the inputs with their units and where each came from (a key of a configuration file, a field of the design or the program), the steps, what the result was checked against (actual, limit, margin) and the assumptions it rests on. It works for the gauge and the voltage drop of a wire, the length of a wire, the mass, the bill of materials, the contact current, the readiness of a harness for building and its eight checks, the test limits, the pin a signal got, why interfaces share a harness, the labels, the colour of a wire, the shield groups and the limit of every design rule. `--json` prints the same as data.
- In the editor: the **Show the calculation** part of the Why tab, the **Explain** button of the Checks tab (for every rule) and an Explain window.
- The code that makes a number is the code that explains it, and a test compares each explanation with the number it explains, to the last digit.
- Every kind of explanation has a page in `docs/models/`; `tests/test_models_docs_complete.py` fails when one has not.

### 2. Assumptions and settings

- `harness-design-studio settings DIR` lists every setting a result depends on: its value, unit, source (your project, the tool's default or not set), range and what depends on it. After them: the assumptions built into the tool (31, each with an ID) and the fixed definitions (the AWG formula, the tolerance of a comparison). `--set FILE.KEY=VALUE` changes a value and refuses one out of range. **Help > Assumptions...** shows the same in the editor.
- The numbers that were built into the program are settings now (62 in all), and a test fails on a number in a calculation that is neither a setting, a definition nor a listed exception.
- 14 assumptions are still built in. They are listed and documented, not changeable.

### 3. Selectable models

- New optional file `config/model.json`; every key has today's behaviour as its default. You can choose which wires the bundle factor counts (`bundle_basis`), the length model, the voltage-drop model (with the resistivity at the ambient temperature), the mass model, the order in which interface categories get pins, and which checks stop a harness from being ready to build. The conductors counted in the drop and the service loops per wire are settings too.
- An explanation names the model in force. A model that is not chosen changes nothing. Page: `docs/models/selectable-models.md`.

### 4. Units

- The cross-section in mm² is shown beside every AWG gauge a person reads (`24 (0.205 mm²)`), on screen and in explanations. **The written files keep the plain gauge.**
- Every column of the open data has its unit in the heading. Imports read lengths in `mm`, `cm`, `m`, `in` or `ft` (`--unit`) and masses in `g`, `kg`, `lb` or `oz`, and say which unit they used and whether it was given or assumed. Page: `docs/models/import-units.md`.

### 5. Workflow

- `harness-design-studio workflow DIR` and the Next step page (a disclosure that is closed until you open it) show the nine steps of the tool, what each uses and makes, the intermediates you can look at (and, where the tool allows it, change) and the state of each step, worked out from the project. The Next step page now shows a quiet line with the number of engineering values still pending, and a **Set the values...** button, in every role. Page: `docs/user-manual/follow-the-workflow.md`.

### 6. Overrides and the change journal

- A gauge, wire type, colour or length that you set by hand on a generated wire is an **override with a reason**. Without a reason the tool refuses (Edit wire tab, *Edit all wires*, `override DIR WIRE FIELD VALUE --reason TEXT`). Generation keeps what you overrode. An explanation starts with *Overridden by the engineer*: your value, your reason, the value the design would give and what yours does to the current limit and the drop. Overrides are flagged in the wire table and list, the cut list, the build workbook, beneath the drawing and in the release record.
- A **change journal** (`journal.json`; `harness-design-studio journal DIR`; **Help > Change history...**) records who changed what, when, from what to what and why, for design inputs, configuration values, overrides, waivers, part approvals, releases and extensions. It is append-only and checked (a changed, removed or inserted entry makes `validate` report a damaged journal), and no hash and no written output holds it, so the same design still gives the same files. `new` starts one unless you pass `--no-journal`.

### 7. Deviations

- An error of an electrical rule (wire and contact current, voltage drop, bundle current, connector and wire voltage, temperature margin) can be accepted as a **recorded deviation** with a reason (`harness-design-studio deviation`, *Accept as deviation...*). It stays visible, marked DEVIATION, on every list and output, no longer blocks a release, and does not meet the requirement.

### 8. Provenance and open data

- `harness-design-studio export-data DIR --out FOLDER` writes every intermediate and final result as a JSON and a CSV file with units: sizing, lengths, segmentation, pin allocation, rule results, findings, readiness, mass, bill of materials, test limits, parts, settings, the configuration files as the tool used them and a provenance file with the tool version, the model hash and the SHA-256 of every file. `docs/examples/open-data/reproduce.py` recomputes the sizing from a folder alone, with no import of the tool.
- A **run record** (`--run-record`: time in UTC, operator, tool version, platform, model hash, extensions) is written beside the outputs and is in no hash, so the same design still gives byte-identical files.

### 9. Imports

- Every import that is applied is recorded in `imports/records.json`: the source name and its SHA-256, the rows read and dropped (with the reason), the values converted (as written, unit, as stored), the columns read and left out, and the unit. `harness-design-studio imports DIR [--check]` says whether a source has changed since (*unchanged*, *source changed*, *source not found*); the import wizard and the Next step page say so too.
- Every file import prints, before the rows, what it read, the columns it left out and the unit; `import-lengths` echoes every converted value (`5.0 mm = 0.005 m`). The parts import reads ratings; the netlist import keeps the pin type and the name of the schematic; the tool's own CSV files can be imported again.

### 10. Scripting

- `harness_design_studio.api`: a Python interface with no Qt, no printing and no exit, for loading a project, generating, checking, exporting, explaining and the rest. `--json` on every command that has a result in data form. Three worked examples in `docs/examples/scripting/`. The interface is version 1 and its names, signatures and result fields are frozen by a test; it is young and has had no user but its own tests and examples.

### 11. Extensions, and the trust model

- Rules, output tables and lookup tables can be added **as data**, in `extensions/*.json`, in a small expression language with its own parser (no `eval`). They are the project's own rules, with an `x-` ID; the 39 built-in rules are not changed.
- **Python plug-ins** (`extensions/plugins/NAME.py` or an installed package) are never loaded unless the project enables them **and** you trusted that exact code (`harness-design-studio trust`; the trust is kept per user and computer, keyed to the SHA-256 of the code). Every enabled extension is named with its version and SHA-256 in `extensions --json`, the provenance file and the manifest.
- **A plug-in runs with your rights and is not sandboxed.** The trust prompt names the code; it does not limit it. Read a plug-in before you trust it. Page: `docs/user-manual/extend-the-tool.md`, `docs/SECURITY.md`.

### 12. As-built capture (AIT)

- Optional `asbuilt/records.json`: per harness, part lot, wire, connector, pin and test, the serial numbers, the lots, the cut and strip lengths, the crimp tool and its calibration ID, who built and who inspected, the measured continuity, insulation and test voltage of each test, and notes. `export-asbuilt` writes a sheet to fill in; `import-asbuilt` reads it back and echoes what it read; `asbuilt DIR` reports what is missing, out of its limit and different from the design. The tool never says that something passed or is compliant, and it applies no tolerance to a cut or strip length. A project with records also gets an as-built report and an *As-built* sheet in the build workbook. Page: `docs/user-manual/record-what-was-built.md`.

### 13. Roles

- Three roles: **Systems engineer**, **Electrical engineer** (the earlier Electrical / AIT role; the stored value is unchanged) and **AIT engineer** (build data, build sheets, outputs, as-built records and the workflow; it opens on the Next step page). A role is a set of pages and menu entries; nothing is locked and everything is reachable from the command palette (Ctrl+K). Page: `docs/user-manual/choose-your-role.md`.

### 14. Visible data links

- The links of a project to its sources are visible: the import records above, *source changed* notices, the provenance file, the extension registry (`harness-design-studio extensions DIR`) and the workflow page together show where each value of a project came from.

### What is not in this release, and what the owner must still decide

- **Not built:** per-key comments, units and sources inside the `config/*.json` files (they are in `settings`, `docs/CONFIG.md` and the registry); an explanation of the *search* that picks a gauge (an explanation shows the limits of the gauge that is on the wire); a stricter sandbox for plug-ins; a length tolerance for as-built records; open data in the Export dialog of the editor (command line and API only).
- **Open decisions for the owner** (`docs/transparency_final_audit.md`): (1) the legacy lock: keep it, or turn it into per-field overrides at the next generation; (2) merge conflicts in `journal.json` and the unauthenticated author; (3) trust for plug-ins and the severity of an extension that is enabled but not applied; (4) the format number 3 of `derivations.json`; (5) the place of the run record; (6) open data in the Export dialog; (7) the apostrophe taken away from text in the tool's own CSV files on import; (8) the read-summary lines of the importers; (9) the strictness of the role split; (10) a length tolerance for as-built records; (11) whether a release freezes or checks as-built records; (12) which values count as needed for an as-built record; (13) per-key metadata in the JSON files; (14) whether the choice of a gauge should be an explanation; (15) whether the Explain window prints the link to its page; (16) whether three limit rules without an assumption ID should get one; (17) the number of the release. The standards and quality process, variants and a sharded `links.json`, and the soldering questions for the AIT engineers stay open (`docs/OPEN_DECISIONS.md`).

### The honest limits

- **Nobody looked at the program on a real display.** The editor was tested with Qt's offscreen platform: texts, widgets and states, not what a person sees. This holds for every new window and page.
- **No compliance and no sign-off is claimed.** The owner has not signed this release off and this page is not a statement of compliance. Standards are cited by ID and title only.
- **The packages are not signed.** Windows SmartScreen shows *Windows protected your PC* (**More info**, then **Run anyway**).
- **The example values are placeholders** for learning, not engineering data. Until your project supplies its own, results say *pending* or *not checked*.
- **The tests were written by the author of the code**, against hand calculations written in the tests. CI runs the whole suite on Linux and Windows; an independent review by a person is still to come.
- **Python plug-ins run with the rights of the user and are not sandboxed.**
