# M6 demo note: change control

**Done**
- **Workflow**: submit for review, release, new revision. Every step needs your name; release and new revision need a comment (at least 10 characters). Steps are plans run through `History`, so they are undoable until saved.
- **Release gate** (plain-language blockers, shown in the dialog and the CLI): verifier or rule errors that belong to the harness, harness plans out of date, undecided gauges, unknown lengths, outputs not exported or exported from an older design, no wires, already released. A release writes a baseline (frozen snapshot), a change log entry, and sets status, approver, checker and date for the title block.
- **Locks**: a released harness, the interfaces it carries, the box pins it uses and the box connectors it mates with cannot be edited or deleted (clear message naming the harness); a new revision (A to B, Z to AA) unlocks it and keeps the old baseline. Regeneration never touches released harnesses.
- **Diff engine**: added, removed and changed objects with field changes, down to pins, wires, shields and segments; between two baselines, the working design and a baseline, or two whole project folders (`harness compare`). Markdown and table output.
- **Consistency**: a released harness that differs from its baseline is an unwaivable error (rule `released-modified`, and `harness check`), so tampering or a bad merge shows up.
- **Outputs**: title block shows author, checker, approver and date; `system/changelog.csv` and `system/revision_report.md` (history plus differences between revisions); the output verifier checks both; the manifest stores a content hash for the release gate.
- **CLI**: `harness review | release | revise | diff | log | compare`. `release` re-exports the outputs so the drawings say "released".
- **Editor**: Harness plans tab shows revision and "released (locked)", with Submit for review, Release…, New revision…, Changes… (list of changes; "Mark on diagram" outlines changed units and interfaces with a dotted halo and a label) and Change log… buttons. On-disk change detection and safe reload were done in M2.
- **Fixes along the way**: generation's input hash no longer includes harness status (a release made every other release's plans look outdated); a review is reset when regeneration changes a harness in review.

**Tested**: 506 tests pass (1 skipped: needs a non-root user). New: gate blockers one by one, release/baseline/changelog, locks (harness, interface, pin, connector, harmless edits still allowed), new revision and second release, review reset, undo of a release, tampered release detected (rule and CLI), save/load of baselines, diff exactness incl. a property test, project compare, output changes and verifier mutation tests, a full CLI cycle, 7 GUI tests. Core coverage 96%. Ruff and mypy strict clean.

**Performance** (stress project): content hash 0.5 s, release gate 1.9 s, lock check 0.02 ms per edit. Edit timings unchanged.

**Placeholders and honesty**: because gauges stay "pending" until derating values (D-11) exist, sat15 and mini3 cannot be released; `sat15_full` (example numbers) can. This is intended. Dates and names are what the user types or the system clock says at that moment.

**UX targets**: release is Harness plans tab, Release, type name and comment, OK; blockers are sentences, not codes. Not reviewed with screenshots or users yet. Open: the diff view is a list (no side-by-side drawing comparison); marks show units, interfaces and harnesses only (not pins or wires); no way to pick two baselines to compare in the editor (working design against a chosen baseline only; the CLI does both).

**Limits and risks**
- The release gate trusts the outputs manifest hash; deep file checking is in `harness verify --outputs`, not in the gate.
- Baselines store the harness and its direct dependencies, not the whole project; a project-wide baseline is available through Git and `harness compare`.
- Two people releasing different harnesses in parallel merge cleanly (separate files) but both append to `changelog.json`, which can conflict; keep entries sorted and resolve by keeping both.
- Windows and Rocky 8 builds are still untested.
