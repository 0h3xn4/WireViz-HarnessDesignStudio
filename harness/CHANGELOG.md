# Changelog

Versions follow semantic versioning. Every project file records the tool version that saved it.

## Unreleased (after 0.1.0)

Changes on `master` since the release of 0.1.0. They are not in the 0.1.0 packages.

- **New example `flatsat`** (`harness new bench --template flatsat`): a complete bench setup of 23 flight and ground units, 44 interfaces, 8 harnesses and 103 wires, shipped generated with EXAMPLE numbers (the configuration files stay marked as placeholders, the parts are example parts). It has ground equipment (checkout system, ground power supply, RF test equipment), four lanes and links between lanes grouped by `per_zone_pair`. A tour with exercises is in `docs/FLATSAT_EXAMPLE.md`; a test checks it against the project.
- **New example `minimal-satellite`**: seven units without redundancy, between `first-steps` and `small-satellite`, as a small realistic starting point. `harness new --list` now sizes its columns to the longest name.
- **New template `design-worksheet.md`** (`harness templates DIR`): a worksheet to plan units, interfaces and the data you do not have yet before opening the tool.
- **Fix: regeneration after a reload** (D-139). A saved project sorts the parts of a harness by ID as text (`S10` before `S2`) but the generator numbered them, so a harness with ten or more shields or segments was reported as *changed* on every generation although nothing had changed. The generator now uses the saved order. A project that has such harnesses shows them as *changed* once on the next generation, and the model hash of such a project changes once; afterwards it is stable. The flatsat example found it.
- **The harness drawing is a wiring diagram** (D-141), after the old wire-by-wire list was found unreadable. Connectors are tables on the left and the right (id, part, gender in words, pin count, the mating box connector, the number and signal of every used pin); the wires between them are curves in their wire colour; each connector pair has a cable block that lists its wires (ID and colour code) with count, gauge and length. Shields, segments, spare pins and the routing sketch follow beneath, and long harnesses continue on further sheets. Wire colours are drawn on a dark outline and also written as IEC 60757 codes, so a greyscale print loses nothing (REQ-OUT-03 reworded; it used to say black and grey only). A wire's colour is data: set by hand, or by the new optional `generation.json` key `wire_colour_by_signal` (for example `{"PWR": "red", "RTN": "black"}`); the tool defines no colours, so an unset wire is grey. The `flatsat` example sets example colours for power and CAN. The drawing preview and the A3 and A4 PDF and SVG are redrawn; their golden digests and the tutorial picture were regenerated.
- **Harness drawing, correctness** (audit of 2026-10-10): a cable block can no longer run into the title block (it was pushed down by half a header and went past the sheet's room on long harnesses), the routing sketch no longer takes room on every sheet (a harness with a branch point and 8 to 12 leaves came out at one wire per sheet) and is left out when it would take more than half a sheet, a wire in two shields keeps both sleeves (nested, darker inside; the flatsat's W002 drew 12 of its 19), a wire with both ends on one side no longer runs backwards through its block, long pin IDs are shortened instead of overlapping the signal, and the shield and spare-pin lines beneath the drawing are wrapped instead of cut off (the ends come first). A connector whose description says "Small plug" is no longer drawn as a coax connector (families are matched as words), and a description that names both genders ("male plug, mates with female socket") takes the first.
- **Safer saving, exporting and importing** (audit of 2026-10-10). Saving and exporting never write or delete behind a link at any depth (a linked sub-folder, a planted `.bak` or temporary file used to let an untrusted project folder overwrite or delete files elsewhere); they refuse instead. Temporary files are unique and exclusive. `harness export` and `harness migrate` refuse a project with damaged files instead of exporting a partial set and exiting 0. A control character pasted into a waiver text is refused, and one in an exported cell is dropped instead of aborting the workbook. An invalid `titleblock.fields` value no longer crashes the drawing. The netlist reader wants a regular file. The check-run helper process starts with `-P`, so a module planted in the current folder is not run. The length cache is bounded (it grew without limit in a long editing session).
- **Wire colours can be set in the editor**: *Edit > Wire colours...* gives each signal name (PWR, RTN, CANH ...) a colour from the IEC 60757 list; it is saved as `generation.wire_colour_by_signal` (one undo step), the wires take it the next time the harnesses are generated, the wire list has a *Colour* column and the drawings draw it. Nothing is preset by the tool. A wire between two different signals (`TX+/RX+`) takes the colour of the first. The colour table moved to `core/wirecolours.py`.
- **Shields are drawn as sleeves on the harness drawing** (D-141): the wires of a shield sit together in their cable block under a grey jacket that carries the shield's ID and kind, and each end shows how it is terminated (solid bar: 360 degree backshell, lead: pigtail, cross: floating). The shield list beneath the drawing stays.
- **Diagram: routing and focus** (D-140). Units no longer overlap in either mode (a unit's room is the taller of its guided and expert heights). Links are routed together as horizontal and vertical lines with rounded corners: each leaves on the edge that faces its other end, joins a trunk in the gutter between lanes and runs side by side with the others of its lane pair. Selecting a unit or a link puts its links in focus and fades the rest; a click on the background or Escape ends it; it works together with *Show*.
- **Diagram: pictures, not text** (D-140). Every kind of link has its own small picture on the link line (bolt for power, wave for analog, bus for CAN, ...); paired-signal links are drawn as two lines and redundant ones stay dashed. A voltage or current shows next to the picture only when it was entered (in a dense diagram for selected, focused or hovered links; *View > Show all link labels* for all); hovering a link says in words what it is. Every connector family has its own picture (flange with screw holes and shell: a tapered D for a D-sub, a rounded block for a Micro-D, circular, RJ45, coax) sized by its pin count. A key under the diagram and the palette show the pictures.
- **Diagram: unit layout and gender** (D-140). In Expert mode a line down the middle separates the left side from the right side, and each port row reads designator, connector picture, pin count; a unit is 240 px wide (lanes 470 px) and a connector row 28 px high. Units in Guided mode show their connectors as small pictures. Gender is black or white: a male connector (pins) is solid, a female (sockets) an outline, a connector without a gender a dashed outline. A connector made from a unit template now takes its gender from its library part when the part says male or female (it was *unspecified*), and the generator gives a cable connector the opposite; a harness that had *unspecified* connectors shows as *changed* once on the next generation. The mating matrix has a *Cable gender* column. The `flatsat` and `minimal-satellite` examples carry an example 28 V on their primary power links. Rules without Qt: `core/routing.py`, `core/describe.py`; pictures: `gui/glyphs.py`, `gui/legend.py`; tests: `tests/test_routing.py`, `tests/test_describe.py`, `tests/test_gui_readability.py`; pictures in `docs/FLATSAT_EXAMPLE.md`.
- **`ops_add_unit` accepts `unit_id` and `name`**, so a unit made from a template can get its own ID and name.
- **Documentation for newcomers**: `docs/LEARNING_PATH.md` (nine steps from install to release, each with a "done when"), `docs/CHEATSHEET.md` (one page), a fuller `docs/INSTALL.md` (supported-system check, checksums, a first five-minute check, troubleshooting), three FAQ starters, and pointers from the README, the tutorial and the in-app guide. The commands and the quoted model hash of the tutorial are unchanged.
- **Repository front page**: the page of this repository (`docs/README.md`) starts with a section on Harness Design Studio, states that the tool was created mainly by an AI (Claude) at the direction of the repository owner, and says how it relates to WireViz (separate clean-room codebase in the WireViz fork, WireViz YAML as an export target). The original WireViz documentation follows unchanged. The same two notices are at the top of `harness/README.md`.
- **CI**: for changes that touch only Markdown directly under `harness/`, Markdown under `harness/docs/` or anything under `harness/compliance/`, the full suite and the package jobs are skipped and a `docs` job runs the checks that read documents (D-138). Any other change runs everything.
- **Records**: `compliance/SIGNOFF.md` has a Publication section for 0.1.0 (merge commit, tag, release page); `docs/RELEASE.md` has a step for tagging and publishing a release; `docs/SECURITY.md` says the SBOM ships with every release.
- **Release check**: the version step skips an `Unreleased` section when it compares the changelog with the version.

## 0.1.0 (first release, 2026-10-09; released by the owner with the engineering decisions still open, see compliance/SIGNOFF.md; not a statement of compliance)

This is release candidate 0.1.0rc8 without the `rc`, plus the note below. The program is unchanged: results differ from rc8 only in the stamps (version, model hash). **Still open at this release**: the harness boundary rule (D-10) and the title block (D-15) are at their defaults; the real derating and EMC values (D-11) and the approved parts list (D-12) have not been supplied, so results rest on placeholders and example parts unless a person has reviewed them (a release of a harness needs a written reason, D-135 and D-136). Waived by the owner and not done: independent verification and validation, the formal reviews, usability sessions, the screen-reader pass and the clean-machine installation test; the packages are unsigned (`compliance/DEVIATIONS.md` T-18 to T-31). Platform: Ubuntu 24.04 and newer.

- **Editor timings re-measured** (`python -m tools.bench_gui`): the benchmark now times undo and redo over whole add / undo / redo cycles instead of one sample. At stress size (200 units, 2,000 interfaces) every edit is under 100 ms and undo is 46 to 59 ms; the earlier "undo about 200 ms" was the one-off cost of the first undo after start-up. UX log item Q16 is closed. No change to the program itself.

## 0.1.0rc8 (release candidate; signed off by the owner on 2026-10-09 with the engineering decisions still open, see compliance/SIGNOFF.md; not a statement of compliance)

This release candidate adds the release gate for parts (D-136) and two fixes from the trial to rc7. Results are unchanged; only the stamps (version, model hash) differ.

- **Release gate for parts (D-136)**: a harness cannot be released while it uses a part that is missing from the parts list, not approved, or marked as unverified example data, unless the person releasing gives a written reason (`harness release ... --accept-unapproved-parts REASON`, or the second field in the release window). The reason and the first part IDs are kept in the change log and the baseline, like the reason for placeholders (D-135). Approved, verified parts need nothing.
- **Fixes from the trial**: the wire current check now uses the table of bundle factors (Table 6-41) when it is set, as the wire sizing does, instead of the single `bundle_derating` factor (with both set, the two used to disagree); the import of segment lengths explains the cause when every row fails on the harness name because the columns are in another order (the columns are read by position: harness, segment, length).

## 0.1.0rc7 (release candidate; not yet signed off by the owner)

This release candidate adds the release gate for placeholders (D-135) to rc6. Results are unchanged; only the stamps (version, model hash) differ.

- **Release gate for placeholders (D-135)**: a harness cannot be released while a configuration file is still marked `"placeholder": true`, unless the person releasing gives a written reason (`harness release ... --accept-placeholders REASON`, or the new field in the release window). The reason and the names of the placeholder files are kept in the change log and in the baseline. A project whose values an engineer has reviewed (every mark cleared) releases as before. Existing released harnesses are not affected.

## 0.1.0rc6 (release candidate; not yet signed off by the owner)

This release candidate renames the product (Harness Design Studio), adds a vulnerability scan and a second, uninstrumented test run to the release check, and carries the compliance records of the ECSS/ESCC audit follow-up. Results are unchanged; only the stamps (version, model hash) differ.

- **New name: Harness Design Studio**, everywhere: window title, About box, application menu entry, documents, installer text, and now also the names behind them: the Python package is `harness_design_studio` (was `harness_tool`), the distribution, `.deb` and `.tar.gz` are `harness-design-studio` (was `harness-tool`), and so are the application launcher, the install folders and the desktop and icon files. The short commands `harness` (command line) and `harness-gui` are unchanged. Remove an old installation with the uninstaller of the old version first (the new package does not replace the old `harness-tool` files). Project files are unaffected.
- **Compliance records and release check**: the release check runs the test suite a second time without coverage instrumentation and keeps both results (ECSS-Q-ST-80C 6.2.3.8); it scans the shipped dependencies for known vulnerabilities (D-134: `python -m tools.check_vulnerabilities`, pip-audit as a development dependency, build host only; a scan that cannot run fails the check); the SDD has a generated component table and requirement-to-component trace (`compliance/sdd_components.csv`, `python -m tools.gen_sdd_components`, kept current by a test); `compliance/` gained the family-group worksheet, the organisation record, the risk register and templates for the independent review, the review record, the dependability analysis input and the acceptance of a real harness; `docs/usability/` gained a session schedule and a screen-reader checklist. The owner's decisions are recorded: A-04 (issues adopted), A-05 (plans approved), A-06 and A-08 signing (waived, T-18, T-19), A-14, A-15, A-17 (profile values accepted as a whole), A-18 (missing standards will not be supplied, T-09).

## 0.1.0rc5 (release candidate; not yet signed off by the owner)

This release candidate carries the baseline standards (D-130), the beginner documentation, examples and templates, the faster editor with the rule check in a helper process (D-128), the ECSS/ESCC compliance audit (D-131, `harness/compliance/`) and the UX/UI guidelines work (D-132, D-133). Still open and needing people: the owner's sign-off, D-10, D-11, D-12, D-15, usability sessions, a screen-reader pass and the actions in `compliance/OPEN_ACTIONS.md`.

- **Fixes found by running a 14-unit, 24-interface project through the tool**: the shield rules (`shield-unterminated`, `shield-wrong-end`, `shield-bonding`, `shield-parts`) no longer treat a plain twisted pair as a shield (with a grounding concept of floating ends, every twisted pair was reported as an unconnected shield: 31 false warnings on the reference satellite); the explanation of `unchecked-config` now also covers notes that need an analysis outside the tool.
- **Library source and date (D-133)**: the parts library records where its data come from. `harness library DIR` shows and sets name, version, source and date; `harness import-parts` records the file name and checksum; the editor and `system/provenance.json` show them. Every model hash changes once (the manifest has two more keys): goldens, examples and the tutorial were regenerated; older projects load unchanged.
- **Diagram filters**: besides a signal class, the toolbar filter can now show one connector or one bundle (harness) and fade the rest; it follows a new project and added interfaces.
- **UX/UI guidelines (owner's document, October 2026)**: the editor follows IBM Carbon (colour tokens, square corners, tabs and fields) with the bundled IBM Plex Sans and Mono fonts (D-132); a provenance file `system/provenance.json` in every set of outputs (tool version, model hash, library, settings with placeholder flags, design counts); requirement IDs on findings (card in the Problems panel, `Requirement` column in `drc_findings.csv`); error messages for damaged project files give the line and column; `harness schema FOLDER` writes JSON Schemas of the project files for editors; File > New project from an example; a toolbar filter that shows one signal class and fades the rest. Review of every guideline, with what does not apply to a model-first tool: `docs/UX_GUIDELINES_REVIEW.md`.
- **Compliance audit against ECSS/ESCC (category C), phase 2** (`compliance/`): requirement lists extracted from the supplied standards, gap analysis and compliance matrix; traceability report (`python -m tools.trace`), metrics (`tools.metrics`), configuration file and SHA-256 of deliveries (`tools.gen_scf`), problem reporting, criticality, standards and configuration management documents. Design checking: optional **standard value profiles** (`harness config --apply-profile`, D-131) and eleven new rules (connector and wire voltage, temperature margin, mating cycles, one manufacturer per connector pair, wire specification, power/return separation, bundle current, shield bonding, one bundle per EMC class), each silent without its numbers and listed under *not checked*; sizing can use the bundle factor table; pin allocation can leave an unassigned contact between power and return; the wire list and labels show the EMC class when classes are used; every rule names the standard requirements it serves. Nothing changes for a project that does not use the new settings, except the line `Rules run: 33` in the design rule report.
- **Baseline standards (D-130)**: RS-422, RS-485 and CAN for communication, Micro-D 9, 15, 21, 25 and 31 pin for power and data, Ethernet (RJ45) as the alternative for high data rates, SMA for RF. New library parts (Micro-D 9, 21, 25 and 31 pin, RJ45 male and female), new interface type `ethernet`; units added in the editor get Micro-D connectors sized by what they carry (and an RJ45 for Ethernet, SMA for RF; RF used to get a D-sub). The computer and the payload carry Ethernet, and the sample, example projects, golden files, tutorial and documents follow. Older parts and interface types stay in the library.
- **Documentation for newcomers**: new `docs/INSTALL.md`, `docs/GETTING_STARTED.md` (a 45-minute tutorial whose commands are run by the test suite, with real output and drawings), `docs/CONCEPTS.md`, `docs/FAQ.md`, `docs/CLI.md` (generated from the program) and `docs/README.md` (a map of all documents); README, HOWTO, user guide, IMPORTS, KICAD, ARCHITECTURE, RELEASE, SPEC and PLAN brought up to date (Ubuntu only, helper process, templates). A test checks that every relative link and anchor in the Markdown resolves.
- **Examples and templates**: `harness new [--template blank|first-steps|small-satellite]` creates a project from an example (`--list` shows them) and `harness templates FOLDER` copies the import templates (CSV for interfaces, approved parts and segment lengths, a KiCad netlist and signal map, CI script and GitHub Actions workflow, a review checklist and **demo** engineering values for learning, which stay marked as placeholders). They ship inside the program, packages included; `python -m tools.build_examples` rebuilds the example projects and a test keeps them in sync.
- **Editor speed, with the background check**: the design rule check now runs in a helper process (D-128) instead of a thread, so it no longer stalls edits for 300 to 500 ms at stress size; with it running, rename takes 20 to 50 ms, move 22 to 65, add 55 to 80, undo about 60 and redo about 30. The overview map is drawn from boxes and lines (it painted 2,200 real items, about 300 ms), the problems list rebuilds only when the cards it shows change, and the map and list wait until you pause. Falls back to a thread if the helper cannot start.
- **Editor speed, add/undo/redo**: with the stress project and no rule check running, add unit takes about 60 ms, undo 65 to 110 ms and redo about 35 ms (were 190 to 330). The problems list and tab counts now follow on a 60 ms timer when a project has more than 1000 findings, and are built from one cheap counting pass (82,000 findings: 470 to about 100 ms); counts and open findings are computed once per change; the diagram grows in 256 px steps so one added or undone unit rarely resizes it. Known limit: while the background rule check runs on a project with tens of thousands of findings, the interface can still stall for a few hundred milliseconds (it holds Python's global lock in long native calls); running the check in a separate process would remove that.
- **Editor speed** (stress project: 200 units, 2000 links): renaming a unit takes about 35 ms (was 170 to 230), moving one 45 to 105 ms, a change while the interface table is shown 80 ms (was 370). One edit no longer repaints every unit and link: the lane backgrounds, which are as tall as the diagram, were invalidated on every edit; links whose curve did not change are left alone; the overview map follows on a 150 ms timer; the interface table keeps its rows when only values change. Regression tests count dirty regions and card builds instead of timing.
- **Platform**: Ubuntu 24.04 and newer only (D-127); CI tests on 24.04 only, the release build image is now `Dockerfile.build-24.04`. Editor speed: the problems panel builds only the cards it shows (add/undo/redo 3 to 6 times faster with many findings).
